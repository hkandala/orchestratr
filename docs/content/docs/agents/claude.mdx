`--kind claude`

## Launch

```
claude --dangerously-skip-permissions [--model <model>] [--effort <effort>]
```

`--effort` accepts the values that `orcr models` reports for the chosen model. One model
reports no effort values at all. Pass no effort for that model.

### Environment

orcr removes every `CLAUDE_CODE_*` variable from the environment it gives the agent.

An inherited `CLAUDE_CODE_CHILD_SESSION` disables **session persistence** for an interactive
session, not only the transcript. It removes the transcript file, the prompt history, the
status file at `sessions/<pid>.json`, and the ability to resume.

The status file is orcr's readiness signal and its state source for this kind. Losing it
disables readiness, state and delivery confirmation together.

It happens whenever the herdr server was started from inside another Claude session. That is
the normal case when orcr itself is run by an agent. `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE`
overrides it, and the condition applies only to interactive sessions, but orcr scrubs the
variable rather than relying on either.

## Startup

Claude shows up to four screens before it accepts input. Permission bypass removes none of
them.

| Screen | Removed by |
|---|---|
| Theme picker | `hasCompletedOnboarding` |
| Security notes | `lastOnboardingVersion` |
| Folder trust | `hasTrustDialogAccepted` for that directory |
| Bypass permissions warning | `skipDangerousModePermissionPrompt` in settings |

The first two are separate keys and both are needed. `hasCompletedOnboarding` alone suppresses
only the theme picker. The security notes screen then blocks on "Press Enter to continue", and
nothing in an orcr agent will answer it. Pressing Enter there writes exactly one key:
`lastOnboardingVersion`.

The value of `lastOnboardingVersion` does not have to match the running version. A stale value
works, so a constant is safe.

orcr sets all four. Three are keys it writes to `~/.claude.json`, and the fourth is a setting
it passes in the launch arguments.

For anyone who has already run Claude, the first two keys are usually present and orcr changes
nothing. The trust key is per directory, so a new working directory needs it every time.

### The bypass warning

orcr passes the setting in the launch arguments. It writes no file.

```
--settings '{"skipDangerousModePermissionPrompt": true}'
```

The binary's own schema describes this key as whether the user has accepted the bypass
permissions mode dialog.

Do not use the older `bypassPermissionsModeAccepted` key. It is a one time migration into
the key above, gated on a migration version, and it does nothing on a configuration whose
migration has already run. Setting it globally and per project, five times, did not suppress
the dialog.

### Interactive tools

```
--disallowedTools AskUserQuestion,ExitPlanMode,EnterPlanMode,Workflow
```

Verified live: with these disabled, a request that normally opens a question dialog is
answered in prose instead, and the turn completes.

The flag is variadic. It must be last, or it swallows anything that follows. orcr never passes
a positional prompt, so this is a constraint on argument order rather than a hazard.

The deny list can also be written in settings, and is the same mechanism:

```json
{"permissions": {"deny": ["AskUserQuestion", "ExitPlanMode", "EnterPlanMode", "Workflow"]}}
```

Do not write `permissions.defaultMode: "bypassPermissions"` and expect it to replace the launch
flag. It is not equivalent. That key is honored only from the highest priority settings source
present. A managed or policy settings file that sets `defaultMode` silently outranks it, and
several hosts ignore it outright. Tested on a machine with a managed settings file: the agent
did not enter bypass and the footer showed a different mode.

orcr passes the flag. A setting that can be outranked without saying so is not a way to
guarantee anything.

`askUserQuestionTimeout` accepts `60s`, `5m`, `10m` or `never`, and defaults to `never`. It
bounds the stall rather than removing it, so orcr removes the tool instead.

`dialogExpiry` and `CLAUDE_CODE_USER_DIALOG_TIMEOUT_MS` look relevant and are not. Their own
description says local prompts with no remote client are unaffected, which is every dialog
orcr will ever see.

### The three written keys

Claude is the only kind for which orcr writes to a configuration file.

```
~/.claude.json
  projects["<resolved real path of the working directory>"].hasTrustDialogAccepted = true
  hasCompletedOnboarding = true
  lastOnboardingVersion  = "<any non-empty string>"
```

orcr writes each key only when it is absent, and writes the trust key only for the working
directory of the agent. It writes a temporary file and renames it, so a concurrent Claude
cannot lose the update. The result is the same state that answering the dialogs once produces.

The trust path must be the resolved real path. On macOS, `/tmp/x` must be written as
`/private/tmp/x`. Any other form of the path is silently ignored. There is no inheritance from a
parent directory.

No flag and no environment variable clears the folder trust dialog. Claude itself prints
the instruction to set this key.

When orcr cannot write a key, `orcr agent new` fails before the agent starts. It does not
start an agent that will stop on a dialog whose default answer is to exit.

## Readiness

```
$CLAUDE_CONFIG_DIR/sessions/<pid>.json    exists, and its "status" field is "idle"
```

Claude writes this file only after every startup screen is cleared.

| Signal | When it appears |
|---|---|
| `sessions/<pid>.<hash>.key` | About 70 seconds too early. Present while a dialog is up. |
| `cc-socks/<pid>.sock` | About 70 seconds too early. Present while a dialog is up. |
| `sessions/<pid>.json` | 0.35 seconds after the last dialog is cleared. |
| Session start hook | About 1 second after the status file. |
| Transcript file | Not until the first turn. |

The negative test is what makes the status file trustworthy. During a 71 second run with the
bypass dialog on screen, the key file and the socket both existed and the status file did
not.

A message sent 0.69 seconds after the status file appeared was accepted and answered.

Claude opens no TCP port.

## State

The status file is a live state machine, and orcr reads its state from there.

| File value | orcr state |
|---|---|
| `idle` | `idle` |
| `busy` | `working` |
| `waiting`, with `waitingFor` | `blocked` |

Measured latency from submitting a message to `busy` is 0.37 seconds.

The backend also reports `blocked` correctly for these dialogs, and it is the default source.
The status file adds one thing the backend does not give: the reason. `waitingFor` reads
`permission prompt` for a permission dialog and `input needed` for a question the model asked.
orcr reports that reason because the two need different responses from a person.

When a question dialog opened, the status file showed `waiting` 6.7 seconds before the
notification hook fired.

Claude stops and asks even with permissions bypassed. Bypass removes the permission prompt. It
does not remove the model's own question tool, which opens a dialog and waits indefinitely.
This was reproduced under bypass. A blocked Claude agent is normal, and orcr cannot clear it.

## Message delivery

Before submitting, note the transcript line count as a watermark. Treat a missing file as
zero. After submitting, poll the transcript every 200 milliseconds and accept either record.

| Case | Record |
|---|---|
| Agent at rest | `type` is `user`, and the message content holds the submitted text |
| Agent working | `type` is `queue-operation`, `operation` is `enqueue`, `content` equals the submitted text |

A message sent while the agent is working always produces the `queue-operation` record first.
What happens next depends on the turn.

- If the turn absorbs it, a second `queue-operation` follows with operation `remove` and reason
  `absorbed_mid_turn`, plus an attachment row of type `queued_command`.
- If the turn ends first, the message is then delivered as an ordinary `user` record.

So a mid turn message can produce both records, and a check matching only `user` records misses
the first case entirely. orcr matches either and accepts the earliest. Anything that counts
messages must treat the pair as one message, not two.

Measured latency:

| Case | Delay |
|---|---|
| From rest | 0.59 to 2.51 seconds |
| Mid turn | 0.51 to 0.59 seconds |

Timeout 10 seconds. The worst measured case was 3.07 seconds.

The timestamp inside the record is earlier than the moment the record can be read. Compare
positions in the file, not times inside it.

## Interrupt

One Escape.

Two Escapes at rest open the rewind view, which offers to restore code and conversation to
an earlier point. orcr sends an interrupt only while the agent is working, which is what
keeps it away from that view.

## Transcript

```
$CLAUDE_CONFIG_DIR/projects/<resolved cwd, every / replaced by ->/<session uuid>.jsonl
```

The root is the configuration directory, not the home directory, so it moves with
`CLAUDE_CONFIG_DIR`. The directory name is the resolved real working directory with every
slash replaced by a hyphen, including the leading one: `/private/tmp/work` becomes
`-private-tmp-work`. The file name is the session uuid, which is the same value the status file
reports.

The file is absent while the agent is idle before its first message, and is created early in
the first turn, measured 4 to 8 seconds after submission with the turn still running. It is
not created when the turn completes.

So orcr can start tailing as soon as it submits, and must never read "the file exists" as "the
turn finished".

The session start hook reports a transcript path for a file that does not yet exist. orcr
tolerates a known path with no file.

Never derive a working directory from this path. The directory name is mangled and the
mangling is lossy.

## Session identity

The backend binds the Claude session id at session start, and reports it as an id. orcr
derives the transcript path from that id and the working directory.

The integration hands the backend both the id and the transcript path, and the backend keeps
only the id. Claude is the one kind where a ready made transcript path exists and is
discarded.

## Steering

A message sent while the agent is working reaches the model at the next tool call. If the
turn makes no further tool call, it runs as a separate turn afterwards. Claude's screen calls
this a queued message.
