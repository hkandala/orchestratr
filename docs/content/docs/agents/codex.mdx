**kind value:** `--kind codex`. versions: 0.159 and later, while the app-server offers the methods
the bridge uses (see [checks](#checks)). the integration was measured on 0.159.3. older measurements name their version.

## launch

the pane runs a short script through `sh -c`. the TUI is its last command, so it becomes the
pane's process.

```sh
exec env -u CODEX_SESSION_ID -u CODEX_THREAD_ID -u CODEX_VERSION -u CODEX_PERMISSION_PROFILE \
    -u CODEX_SANDBOX -u CODEX_SANDBOX_NETWORK_DISABLED -u CODEX_NETWORK_PROXY_ACTIVE \
    -u CODEX_EXEC_SERVER_URL <other kinds' markers> \
  ORCR_AGENT_ID=<id> ORCR_BUS=<bus> [CODEX_HOME=<home>] <stall environment> \
  /bin/sh -c '<script>'
```

the script, before shell quoting:

```sh
S=~/.local/state/orcr/run/<id>.sock
/abs/codex app-server --listen "unix://$S" \
  -c 'projects={"<real cwd>"={trust_level="trusted"}}' \
  -c tools.experimental_request_user_input.enabled=false \
  -c tools.update_plan.enabled=false \
  --disable tool_call_mcp_elicitation \
  -c 'shell_environment_policy.set={EDITOR="true",VISUAL="true",GIT_EDITOR="true",PAGER="cat",GIT_PAGER="cat",GIT_TERMINAL_PROMPT="0",CI="1"}' \
  -c 'mcp_servers.orcr={command="/abs/orcr",args=["mcp"],env_vars=["ORCR_AGENT_ID","ORCR_BUS","XDG_STATE_HOME"]}' \
  [-m <model>] [-c model_reasoning_effort=<effort>] <config args> >>"$S.log" 2>&1 &
for i in $(seq 100); do [ -S "$S" ] && break; sleep 0.1; done
( /abs/orcr bridge codex --socket "$S" >>"$S.log" 2>&1; kill 0 ) &
exec /abs/codex --remote "unix://$S" --yolo -C <real cwd> [-m <model>]
```

| part | why |
|---|---|
| `CODEX_HOME` | only when `home` is set. the app-server and the TUI share it. |
| `S` | one socket per agent, in `$XDG_STATE_HOME/orcr/run/` (default `~/.local/state/orcr/run/`, mode `0700`), beside orchestratr's own socket ([transport](/docs/socket-api#transport)). orchestratr writes the absolute path. |
| `app-server` | a private server for this agent. it runs every turn, tool, hook and MCP server, and writes the transcript. the TUI is only a client. its output goes to `$S.log`, off the TUI's screen. |
| `projects=…`, `tools.*`, `--disable …`, `shell_environment_policy.set` | trust, the interactive tools and the stall environment. see [startup](#startup). |
| `mcp_servers.orcr` | the [tools](#tools). an MCP server gets a base environment plus `env_vars` only, so the variables `orcr mcp` needs are named. |
| `-m`, `model_reasoning_effort` | effort must be on the app-server, because a remote TUI does not forward it. `-m` goes on both. |
| `<config args>` | `kind.codex.args`, on the app-server, because only there do thread settings apply. |
| `( … bridge …; kill 0 ) &` | the [bridge](#the-bridge). when it exits, for any reason, `kill 0` ends the whole process group: the pane closes and the agent reads `exited`. an agent whose bridge died would otherwise look alive and never read its inbox. |
| the socket wait | the TUI does not retry a missing socket: it exits with `failed to connect to remote app server`. after 10 seconds the TUI starts anyway, fails visibly, and `agent new` reports the pane. the bridge starts after the wait, and also retries its connect for 10 seconds before it gives up. |
| `--remote … --yolo -C` | the TUI. it sends `--yolo` (the permission bypass) and `-C` (the thread's working directory) with `thread/start`. |

**every thread setting goes on the app-server.** with `thread/start`, a remote TUI sends only
`model`, the approval policy, the sandbox, and these `-c` keys: `allow_login_shell`,
`default_permissions`, `features`, `network`, `permissions`, `sandbox_workspace_write`,
`shell_environment_policy` and `suppress_unstable_features_warning`
(`tui/src/app_server_session.rs:1795`). trust, `tools.*`, `mcp_servers.*`, hooks and effort on the
TUI are silently ignored.

**start the app-server through the person's `codex`.** a wrapping launcher may add `-c` flags for
the provider and authentication. at Meta it adds dozens, and turns ran only when the app-server
was started through it (verified).

### process lifetime

`sh -c` has no job control, so the app-server, the bridge and the TUI share one process group,
which `exec` makes the pane's foreground group. measured on 0.159.3 with herdr 0.9.3:

- when the TUI exits, or the pane is closed, the hangup ends every process within 3 seconds, MCP
  servers included.
- without `exec`, the app-server is orphaned.
- `kill` on a wrapping launcher's pid orphans the real `codex`: the launcher does not forward
  SIGTERM. whoever ends Codex signals the **process group**.

## startup

**directory trust.** Codex shows a trust dialog in a folder it has not seen. `--yolo` does not
remove it, and no environment variable does. a remote TUI reads trust from the server with
`config/read` (`tui/src/onboarding/directory_trust.rs`), so the override goes on the app-server:

```sh
-c 'projects={"<real cwd>"={trust_level="trusted"}}'
```

<Callout type="warn" title="the dotted spelling breaks on a path with a dot">
Codex splits an override key on every `.` (`config/src/overrides.rs:22`). with
`-c projects.<path>.trust_level=trusted`, the cwd `/private/tmp/orcr-trust/a.b/w` became the key
`/private/tmp/orcr-trust/a`, and `config/read` showed no trust (0.159.3). the inline table keeps
the path inside a TOML string: `config/read` showed it trusted, and the person's other `projects`
entries kept. a TOML-quoted key is split the same way. escape `"` and `\` in the path.
</Callout>

the path is the resolved real path: on macOS, `/tmp/x` is `/private/tmp/x`. any other form was
silently ignored (0.154). a git repository root entry covers every folder under it.

**hook review.** when the Codex home holds hooks that are new or changed, the TUI shows a review
screen before it starts the thread. herdr's Codex integration is such a hook, so anyone who
installed it has answered the screen. orchestratr installs no hook, writes no hook trust, and
never passes `--dangerously-bypass-hook-trust`, which would also run the person's untrusted hooks.
[`orcr doctor`](/docs/cli#orcr-doctor) reports the herdr hook when it is untrusted.

**interactive tools.** the three flags in the script, on the app-server. the first key must be a
table: `tools.experimental_request_user_input = false` fails with `invalid type: boolean, expected
struct`. `update_plan` was off by default (0.154), and is set anyway. `request_permissions` is off
unless enabled.

**stall environment.** Codex captures a shell snapshot at startup and applies it after the process
environment, which undoes `EDITOR`. demonstrated on 0.154: an editor held the terminal until it
was killed. `shell_environment_policy.set` is applied after the snapshot, so the seven values are
set there too, in one inline table.

- **the values must be TOML strings.** `-c shell_environment_policy.set.EDITOR=true` makes the
  app-server exit: ``invalid type: boolean `true`, expected a string`` (0.159.3). `CI=1` fails as
  an integer.
- the inline table merged with the `set` entries the person already had (`config/read`, 0.159.3).

## integration

### why `--remote`

the bridge must start a turn from outside the TUI. a second client on an app-server socket is the
only way: the embedded TUI exposes no listener, a hook result is read only at a turn boundary, and
Codex drops an MCP server's notifications (0.159.3, source). so the TUI runs with `--remote`
against a private app-server, and the person and the bridge drive one thread. measured on 0.159.3:

a bridge `turn/start` shows in the TUI as a normal `›` user line. during a bridge turn, the
person's Enter (steer), Tab (queue) and Esc (interrupt) all work, and steers from both sides merge
into one turn. a TUI submit and a bridge `turn/start` 0.3 seconds apart became one turn plus one
steer.

### limits of `--remote`

| limit | effect |
|---|---|
| refused at start | `--no-daemon`, `--add-dir`, `--worktree`, `-c sandbox_workspace_write.writable_roots`. orchestratr passes none. |
| `/cd` | refused for remote workspaces. |
| `!cmd` | runs in the app-server, under its environment and shell policy. |
| `history.jsonl` | the TUI writes its own composer submissions only. bridge messages never appear. |
| app-server crash | the TUI tries to reconnect for 120 seconds, and herdr reports `working` throughout. |
| protocol | `app-server` is labelled experimental, and changes between versions. see [checks](#checks). |

### the bridge

`orcr bridge codex --socket <path>`, in the `orcr` binary. there are no integration files. it
speaks JSON-RPC over a WebSocket on the unix socket, and sends `initialize` with
`capabilities.experimentalApi: true`, as the TUI does. it is a sidecar in the pane's process
group, so it dies with the pane, and the pane dies with it.

1. **find the user thread.** `thread/started` is broadcast to every client. follow the newest
   thread with `parentThreadId == null` and `threadSource == "user"`. this skips subagents, and a
   short-lived thread a managed hook loaded at startup on the test machine. if the bridge
   connected after the TUI's thread started, it checks `thread/loaded/list` with `thread/read`.
2. **register.** add `session` (`{"id": <thread id>, "transcript": <thread.path>}`),
   `integration` (`"2"`, the version: Codex has no files) and `started_at` to the record,
   only if the record file still exists. orchestratr recorded `pid` at launch. on a later user
   `thread/started` (`/new`, `/fork`), rewrite `session`, and `thread/unsubscribe` the old thread,
   or it stays loaded with its own MCP server.
3. **subscribe** with `thread/resume {threadId, excludeTurns: true}`. turn and item events need a
   subscription, and it keeps the thread loaded.
4. **take messages** by mode (below).
5. **watch the app-server.** when its connection closes, the bridge exits, and the launch
   script's `kill 0` ends the pane. orchestratr does not restart an app-server, although the TUI
   rejoins a restarted one ("Reconnected. No input was resent.", verified). when the TUI exits,
   the pane's hangup ends the bridge.

**the negative test.** the TUI sends `thread/start` only after its trust check and hook review
(`tui/src/lib.rs`: trust at 1807, hook review at 2012, `App::run` at 2031). so the record cannot
appear while either screen is up. not measured in remote mode. on 0.154 with the embedded TUI, the
thread's writer lock never appeared in six runs abandoned at either screen. the thread starts at
TUI startup, before any prompt: its MCP server started 1.8 seconds after the app-server (verified).

### delivery

| mode | at rest | while working |
|---|---|---|
| `steer` | `turn/start` | `turn/start`. on a running thread it steers, and returns the running turn's id. |
| `followUp` | `turn/start` | held by the bridge. at each `turn/completed`, the oldest held message goes in a `turn/start`: one follow-up per turn. after an interrupt, see [recovery](#recovery-after-an-interrupt). |
| `immediate` | `turn/start` | `turn/interrupt {threadId, turnId}`. at `turn/completed`, `turn/start`. |

`turn/start` takes `{threadId, clientUserMessageId: <msgId>, input: [{type: "text", text: <block>,
text_elements: []}]}`, one message per call, in id order. it returns the turn's id, which is the
`turnId` for `turn/interrupt`. the bridge treats the thread as working from the moment it calls
`turn/start` on an idle thread, not from `turn/started`, so a second message moments later is a
steer into the starting turn, or a held `followUp`.
`<block>` is the `<agent-message>` block, or the `<agent-watch>` block for a message that has a
`watch` field.

**before every hand-over**, including a held `followUp` and a re-hand, the bridge checks that
`<msgId>.json` still exists. `orcr agent stop` deletes undelivered messages before it interrupts,
so this check keeps a stop from starting a new turn.

- **`.accepted`** when `turn/start` returns, or when the bridge holds a `followUp`.
- **`.delivered`** at `item/started` on the followed thread with `item.type == "userMessage"` and
  `item.clientId` equal to the message id. it fires when the input enters
  the model's context: a steer sent during `sleep 15` was announced 13 seconds later, when the
  tool returned (0.159.3). the person's messages carry TUI uuids, which never collide.
- **an empty `immediate`** only interrupts, and never starts a turn. on an idle thread the bridge
  writes `.accepted` and `.delivered` at once and does nothing else. on a working thread it calls
  `turn/interrupt`, writes `.accepted` when the call returns, and `.delivered` at
  `turn/completed`. an empty `immediate` older than 10 seconds by `sent_at` when the bridge takes
  it is marked `.accepted` and `.delivered` and ignored, so a stale interrupt never aborts a later
  turn. an empty `immediate` is never handed over again. a running command survives the interrupt as a background terminal (0.159.3).
  stopping it needs Codex's own stop command, typed by a person.

**the first turn.** `thread/resume` fails with `no rollout found for thread id …` until the
thread has run a turn. the bridge retries it at each broadcast `thread/status/changed` for the
thread, and every 50 milliseconds after its own first `turn/start`. measured: success at 0.08
seconds, `item/started` at 1.34 seconds. without slow hooks the item can come first. so on a
thread that has never run, the bridge writes `.delivered` when `turn/start` returns: the message is
the first input of the turn it starts.

### recovery after an interrupt

any interrupt, the person's Esc or an `immediate`, silently drops a bridge steer that has not
reached `item/started`. measured on 0.159.3: after Esc, it got no `item/started` and no turn in 25
seconds. the TUI shows only its own pending steers, and re-sends only those.

at `turn/completed` with status `interrupted`, the bridge first sends the `immediate` message, if
any, once. then it calls `turn/start` again, in id order, for every message it already handed over
that is not `.delivered` and whose file still exists. without an `immediate`, the first of these
starts the next turn. held follow-ups were never handed over, so they are not re-sent, and they
stay held until the next `turn/completed`: they never join the turn the bridge just started. if
no turn starts here (no `immediate` with text, nothing to re-hand), the bridge sends the oldest
held follow-up at once, so an Esc or an empty `immediate` never leaves follow-ups held forever.

### tools

`orcr mcp`, from `mcp_servers.orcr` on the app-server. `from` comes from `ORCR_AGENT_ID`, not
from the per-call `_meta.threadId`, because the inbox is keyed by the agent id. the server starts
one identical MCP process per loaded thread. a crashed one is not restarted: its calls fail with
`Transport closed` (verified).

### checks

the [check](/docs/integrations#checks) runs `codex app-server generate-json-schema` and refuses
install and `agent new` when a method, notification or field the bridge uses is missing:

- requests: `turn/start` with `clientUserMessageId`, `turn/interrupt`, `thread/resume`,
  `thread/unsubscribe`, `thread/loaded/list`, `thread/read`;
- notifications: `thread/started`, `thread/status/changed`, `turn/started`, `turn/completed`,
  `item/started` with `clientId`.

### traps

- **any process of the same user can drive any agent's app-server.** the path in orchestratr's
  `0700` folder is a symbolic link to a `0600` socket in `/private/tmp/codex-daemon-<uid>/`, a
  `0700` folder (verified on 0.159.3). there is no other authentication. that is the trust level
  of the bus.
- **the socket path is a link**, and `connect` follows it, so the `sun_path` limit (104 bytes on
  macOS) applies to the link's path. stale `.lock` files collect in the `codex-daemon` folder,
  and are harmless.
- **the person's hooks run on every injected message.** on the test machine, `UserPromptSubmit`
  hooks added about 0.8 seconds to each steer.
- **`mcp_servers.orcr` merges** key by key with a person's own `[mcp_servers.orcr]`.
- **a provider or authentication error** ends the turn with status `failed`. the message was
  delivered.

## state

from herdr's Codex integration, which reads the terminal title: a spinner while working
(`⠼ work`), the bare title at rest. verified with `--remote` on 0.159.3, including turns the bridge
started. the screen body is not enough: during a turn that streams text and calls no tool, it
matches the body at rest (0.154).

herdr's Codex hook runs in the app-server, and needs the pane's `HERDR_*` variables. that is why
the app-server starts in the pane, not from the orcr server: without `HERDR_PANE_ID` the hook
exits early.

## transcript

```text
$CODEX_HOME/sessions/<year>/<month>/<day>/rollout-<timestamp>-<thread id>.jsonl
```

written by the app-server. the path comes from `thread.path` at registration, a field Codex marks
unstable. the file exists after the first turn.

- prompts come from `event_msg` (`user_message`, or `item_completed` with a `UserMessage`), never
  from `response_item` user records, which also carry `<environment_context>` and `AGENTS.md`.
- skip `developer` records tagged `hooks.additional_context`.
- a turn's outcome is its last `task_started`, `task_complete` or `turn_aborted`.
  `task_complete.last_agent_message` is the answer. an `error` field is a provider failure.
- input sent mid turn reaches the file only when the running tool returns: 17.82 seconds in one
  measurement (0.154). fine for reading, and the reason delivery uses `item/started`.

## session identity

the thread id is the session id, a UUIDv7. the bridge learns it from `thread/started`, before any
transcript exists, and follows `/new` and `/fork`. `/new` was verified, including a bridge
`turn/start` on the fresh thread before its first turn. `/resume` broadcasts no `thread/started`.

orchestratr never reads Codex identity from herdr. herdr's binding is right here, because each
agent has its own app-server. under the shared daemon, one hook reported every TUI's thread to the
first pane (herdr-web-ui, 0.157.1).

## model catalogue

```sh
codex debug models
```

prints the catalogue as JSON in about half a second, with no server and no turn. filter on
`visibility == "list"` to match what the agent offers. not `--bundled`, the compiled-in list, which
is out of date. not the model route files in the Codex home, a small overlay that lacks most effort
values.

## what is not used, and why

| not used | why |
|---|---|
| typed keys | the design rule. also, two escapes at rest open the backtrack view. |
| the shared app-server daemon | any `-c` makes the TUI skip it. the private server is the same binary. |
| `thread/queue/add` for `followUp` | after an interrupt, a queued item waits until a later turn completes normally, and the TUI shows nothing. once, one vanished. |
| `turn/steer` | needs `expectedTurnId`, and races the turn's end. `turn/start` does not. |
| hooks and `codex queue` | a 10 second poll, no `immediate`, a steer the TUI does not show, and it breaks once a daemon runs for the same home. |
| the bridge inside `orcr mcp` | one MCP process per loaded thread: `/new` delivered a message twice. no restart after a crash, and no thread id. |
| the bridge in the orcr server | the app-server must start in the pane for herdr's hook. a sidecar also works while the orcr server is down. |
| `thread-writer-locks/`, `history.jsonl` | lock files outlive their process and name no pane. `history.jsonl` never sees bridge messages. |

## not verified

- the negative test in remote mode, and a bridge that connects after the TUI's `thread/started`.
- trust on the app-server alone. the source says it is enough. every live run also passed it to
  the TUI.
- `-m` on both commands, and whether `thread.path` is set before the first turn.
- `/resume` and `/fork` in a remote TUI, and how the bridge follows them.
- subagent threads with their own MCP processes, and `turn/start` during auto-compaction.
- the order of an `immediate` and re-sent steers.
- a first message sent with the person's first prompt. it becomes a steer, and is marked delivered
  early.
- the exact tool name the model sees for `orcr mcp`.
- whether the model list needs pagination. it returns a cursor, and one page holds every model.
