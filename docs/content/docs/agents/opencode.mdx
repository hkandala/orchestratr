title: "OpenCode"

**kind value:** `--kind opencode`

## launch

```sh
opencode --yolo -m <provider>/<model> --hostname 127.0.0.1 --port <port>
```

### version requirement

OpenCode must be 1.18.29 or newer. the herdr integration for OpenCode exports an entry point
that older builds never call, so on an older build the integration loads, reports nothing, and
everything it supplies is silently absent.

[`orcr doctor`](/docs/cli#orcr-doctor) checks the version and refuses below the floor.

<Callout type="warn" title="a binary named opencode is not always OpenCode">
during this design work the binary with that name was a redirect stub for an older fork, and
every conclusion drawn from it was wrong. set `kind.opencode.binary` in the
[configuration](/docs/configuration#binary) to point at a specific build.
</Callout>

### permissions

`--yolo`, `--auto` and `--dangerously-skip-permissions` are three spellings of one boolean,
combined into a single value. OpenCode has no setting between asking and not asking, so there is
no safer intermediate mode to prefer here.

### effort

**effort cannot be set on the command line for an interactive session.** a third path segment on
`-m` does not select a variant. it is appended to the model identifier and breaks the run. the
`--variant` flag that does select one exists on the non-interactive `run` subcommand only, and
is absent from the interactive option list.

effort comes from configuration, passed inline so that nothing the person owns is modified:

```sh
OPENCODE_CONFIG_CONTENT={"agent":{"build":{"model":"<provider>/<model>","variant":"<effort>"}}}
```

this is merged as the last configuration layer, so it overrides the person's own settings for
this process and changes no file. confirmed in source: the loader calls `merge` for that layer
rather than replacing.

`build` is the name of a mode. OpenCode calls its modes agents, and a mode is not a model. the
`-m` flag never accepts one. orchestratr uses the word agent for a session it starts, so the two
meanings collide in this kind only.

proven on the wire rather than on screen. with the key set, the outgoing request carries
`"reasoning": {"effort": "high", "summary": "auto"}`. without it the field is absent. the
database and the HTTP API both report the same resolved variant.

three rules, each of which fails quietly if broken:

1. **`variant` needs `model`.** the variant applies only to the agent's configured model, so
   both keys must be present together. with `variant` alone the API reports the variant while
   the request goes out with no reasoning field at all. this is the trap: every observable
   except the wire says it worked.
2. **the model must publish variants.** a variant name that the model does not offer resolves
   to nothing. [`orcr models`](/docs/cli#orcr-models) reports the set per model.
3. **it is fixed for the life of the process.** the value is read at startup, and editing
   configuration under a running agent changes nothing until restart. only
   [`orcr agent new`](/docs/cli#orcr-agent-new) sets it.

a person using the in-session model picker outranks all of this. that explains an agent whose
effort is not what orchestratr set.

### the pinned port

**orchestratr pins an HTTP port.** the interactive program serves its own API on that port.
orchestratr uses it for readiness and for detecting a blocked agent. orchestratr chooses a free
port and records it in the registry.

## startup

OpenCode shows no startup screen when at least one model provider resolves. a provider resolves
from the generated configuration, from stored credentials, or from a recognized API key
variable.

with no provider at all it opens a `Connect a provider` dialog at startup, regardless of how
fresh the configuration is. orchestratr asserts a provider in the configuration it generates, and
treats that dialog as a launch failure rather than something to answer.

given a provider, there is nothing to suppress and nothing to answer.

the full screen notice reported on a fork is fork behavior, not OpenCode behavior.

### interactive tools

two layers, and orchestratr uses both.

```sh
OPENCODE_CLIENT=orcr
OPENCODE_PERMISSION={"question":"deny","plan_enter":"deny","plan_exit":"deny"}
```

the first keeps `question` out of the registered tool list. the gate is on the client name: any
value outside `app`, `cli` and `desktop` works, and `orcr` is one such value.

<Callout type="warn" title="do not set OPENCODE_ENABLE_QUESTION_TOOL">
it overrides the client name gate and puts the `question` tool back.
</Callout>

`plan_exit` is a real tool id, but it is registered only when an experimental plan mode is
enabled and the client is `cli`. under orchestratr's client name it is absent already.
`plan_enter` is not a tool at all, only a permission name, so denying it is harmless and removes
nothing.

the second layer denies them even if registration changes. the variable is merged after the
configuration file, so it wins.

the configuration form works too:

```json
{"permission": {"*": "allow", "question": "deny",
                "plan_enter": "deny", "plan_exit": "deny"}}
```

<Callout type="warn" title="the order of permission rules matters">
rules are a flat list resolved by last match. `"*": "allow"` must come first. put it last and it
re-enables everything that precedes it, which silently undoes the whole thing.
</Callout>

keys accept wildcards, so `"quest*": "deny"` works.

the older `{"tools": {"question": false}}` form also works, and loses to any later `permission`
block.

there is no command line flag for this on any subcommand.

## readiness

send a nonce through the agent's own composer and wait for it to come back.

```text
POST /tui/append-prompt   with a nonce
POST /tui/clear-prompt
```

repeat until the nonce appears in `$XDG_STATE_HOME/opencode/prompt-history.jsonl`.

three details make this work. getting any of them wrong breaks it silently.

1. **the nonce must be at least 20 characters.** that file is appended when the composer is
   submitted, and when it is cleared while holding a draft of 20 or more trimmed characters.
   orchestratr never submits, so the clear is what records the nonce, and a short nonce records
   nothing.
2. **the return values prove nothing.** both endpoints publish an internal event and return true
   immediately, before the interface has processed anything. waiting for the nonce to come back
   out is the proof, not the response.
3. **these endpoints reach the interface even when a dialog is open**, and `clear-prompt` closes
   that dialog. so the readiness check must run before orchestratr considers the agent usable,
   and never as a health check on a live agent, or it can dismiss something a person was
   answering.

for the same reasons, orchestratr does not use these endpoints to deliver a message.

this round trip is the only signal that is not optimistic. everything cheaper fires early:

| signal | how early |
|---|---|
| the backend's own readiness answer | 25.4 seconds |
| log file appears | 15 seconds |
| database file appears, port opens | 11 seconds |
| lock directory appears | 10 seconds |
| `/tui/*` returns HTTP 200 | still starting |

the HTTP server answers before the terminal interface can accept input, so a bare health check
is not readiness. only the round trip through the composer proves the interface is live.

the terminal title becomes correct about 0.63 seconds early and is a usable cheap fallback.
orchestratr uses the round trip, because the port is already pinned for the blocked check and
the round trip costs one more request.

## delivery

the delivery record is in the SQLite database.

```text
$XDG_DATA_HOME/opencode/opencode.db          release build
$XDG_DATA_HOME/opencode/opencode-local.db    development build
```

the file name carries the release channel. set `OPENCODE_DB` at launch to pin it, so
orchestratr polls the file the agent writes.

take the watermark as the current time in milliseconds. after submitting, poll every 200
milliseconds, joining `part` to `message`:

```text
part.time_created >= <watermark>
  and message.data ->> '$.role' = 'user'
  and part.data   ->> '$.type' = 'text'
  and part.data   ->> '$.text' matches the submitted text
```

| case | delay |
|---|---|
| from rest | 0.34 seconds |
| mid turn | 0.38 seconds |
| first message of a new agent | 0.43 seconds |

timeout: 5 seconds.

a message sent in the middle of a turn was readable 50.8 seconds before the running 60 second
tool returned. OpenCode records a message when it accepts it, not when it acts on it.

### reading the database safely

the database uses write ahead logging. open it read only, with `mode=ro`.

<Callout type="warn" title="never open the database with immutable=1">
`immutable=1` tells SQLite to ignore the write ahead log, and recent writes live there. one
observed run had a 757 kilobyte main file and a 609 kilobyte log.
</Callout>

do not poll the `session_input` table. it is always empty.

## state

| question | source |
|---|---|
| is the agent working | the backend, from its own screen rules |
| is the agent waiting for a person | `GET /permission` on the pinned port |

blocked is available over HTTP only. the `permission` table stays empty both while a request is
pending and after it is answered, and the event table carries only message and session events.

the backend has no idle rule for this kind, so its idle answer is a default rather than an
observation. orchestratr does not depend on it. readiness comes from the round trip and delivery
comes from the database, and neither consults the backend's idle answer. see
[state](/docs/readiness-and-delivery#state).

## interrupt

two escape key presses, with the second within 5 seconds of the first.

one escape is ignored. a counter resets after 5 seconds, so two escapes further apart than that
do nothing: 2 seconds apart interrupted in 0.45 seconds, 6 seconds apart did nothing.
orchestratr sends them as one burst, which is the safe end of that window rather than a
requirement.

the escape is dropped entirely when the agent is idle, when a permission or auto overlay is
visible, or when the composer does not have focus.

an escape at rest does nothing here, but escape is also the dismiss key for the command palette,
the model picker and the permission dialog, so orchestratr sends it only while the agent is
working. see [`orcr agent interrupt`](/docs/cli#orcr-agent-interrupt).

## transcript

the conversation is in the same database as the delivery record. this kind writes no transcript
file.

[`orcr agent read`](/docs/cli#orcr-agent-read) selects the parts of one session, and joins `part`
to `message` for the role.

```sql
select p.time_created, m.data ->> '$.role', p.data
  from part p
  join message m on m.id = p.message_id
 where p.session_id = <session id>
 order by p.time_created, p.id
```

order by `time_created` and then by `id`. time alone is not enough: in one database, 1122 of
6654 parts shared a millisecond with another part of the same session, and one millisecond held
18 parts.

the tie-break works because parts written in the same millisecond share an id prefix and end in a
counter that increases in write order.

never order by `id` alone. the prefix is not ordered across sessions. in the same database, no
row held the same position under id order and under time order.

`part.data` carries the type: `text`, `reasoning`, `tool`, `step-start`, `step-finish` and
`file`. only `message` carries the role.

## session identity

the backend never binds a session for this kind, so orchestratr finds it itself.

take `part.session_id` from the row that confirms the first delivery. no session row exists
before the first submission.

the fallback is `session.directory`, matched against the resolved real path of the working
directory. on macOS that is the `/private` form.

## model catalogue

start `opencode serve` on a free port, read `GET /config/providers`, and stop the process.

this is the only kind whose catalogue needs a server, and the only source that carries the per
model variants where effort lives. orchestratr stops the server before the command returns.

`opencode models --verbose` also lists variants and needs no server, but it has no structured
output mode. its lines interleave with pretty printed blocks that a reader must brace match, and
it omits the provider metadata and the default model map.

variants are not in the model cache on disk. the cache format has no variant field. they are
produced at runtime.

## steering

a message sent while the agent is working reaches the model at the next tool call. if the turn
makes no further tool call, it runs as a separate turn afterwards, 53 milliseconds after the
first one ends. OpenCode's screen calls this a queued message.

## not verified

- whether the HTTP event stream and the database agree on ordering under load.
- whether the round trip readiness check is safe when a person is attached and typing.
