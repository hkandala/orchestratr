**kind value:** `--kind pi`

Pi is the reference kind. every part of the [contract](/docs/integrations#the-contract) works
from inside the process through Pi's public extension interface. unless a line says otherwise,
the claims below were measured on Pi 1.0.0 with herdr 0.9.3.

## launch

```sh
exec env -u <session markers> \
  ORCR_AGENT_ID=<id> ORCR_BUS=<bus> [PI_CODING_AGENT_DIR=<home>] <stall environment> \
  <abs path>/pi --approve --session-id <id> -e <dir>/pi.ts \
  [--model <provider>/<model>] [--thinking <level>] <config args>
```

| part | why |
|---|---|
| `env -u` | removes every kind's markers. for Pi these are `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`, `PI_CODING_AGENT`, `AI_AGENT` and `PI_HERD_PARENT`. Pi exports `PI_SESSION_ID` and `PI_SESSION_FILE` to every child process. a leaked `PI_HERD_PARENT` makes pi-herd in the new agent stop it with `SIGTERM` when that parent ends. |
| `ORCR_AGENT_ID`, `ORCR_BUS` | the extension does nothing without both. |
| `PI_CODING_AGENT_DIR` | only when `kind.pi.home` is set. see [configuration](/docs/configuration). |
| `<abs path>/pi` | the process must be named `pi`. herdr binds its Pi integration by process name. run as `pi.real`, which is the real binary behind one launcher, herdr reported no agent and the state `unknown`. through a link named `pi`, it reported `idle`, `working` and `blocked`. |
| `--approve` | trusts the project's own files for this run. see [startup](#startup). |
| `--session-id <id>` | the agent's id is also the first session id. Pi creates the session when it is missing, and opens it when it exists. see [session identity](#session-identity). |
| `-e <dir>/pi.ts` | loads the orcr extension from the installed version folder. |
| `--model`, `--thinking` | the model is always `<provider>/<model>`. `--thinking` is Pi's effort argument, with values per model. |

no permission bypass is needed. Pi has no permission prompts.

## startup

### the trust dialog

Pi shows no trust dialog in an empty new directory. it shows one only when the working directory,
or an ancestor of it, holds one of these:

- a `.pi/settings.json`
- a `.pi` subdirectory for extensions, skills, prompts or themes
- a `.pi` system prompt file
- an `.agents/skills` directory

`--approve` removes it. this is the same decision as the permission bypass: trust the directory
the person asked orchestratr to run the agent in.

<Callout type="warn" title="--no-approve also removes the dialog, and is not a substitute">
`--no-approve` removes the dialog by skipping the project's settings, extensions, skills and
system prompt. that silently discards the setup a person built.
</Callout>

### interactive tools

none to deny. Pi's built-in tools are `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`, and
`powershell` on Windows. none of them waits for a person.

### the stall environment

the shared one. what can still stop a Pi agent is an extension that opens a dialog, such as a
confirm before each shell command. no launch argument prevents it. the integration reports it
as `blocked` (see [dialogs](#dialogs)). a person clears it with
[`orcr agent attach`](/docs/cli#orcr-agent-attach).

## integration

an **extension**: one TypeScript file, `pi.ts`, loaded with `-e`. Pi loads an extension given on
the command line whatever the project trust says. no Pi configuration file is touched.

the extension returns at once unless `ORCR_AGENT_ID` and `ORCR_BUS` are set, and does nothing
outside the interactive mode (`ctx.mode !== "tui"`), so `-p`, json and rpc runs are untouched.

### registration

at `session_start`, the extension reads `agents/<id>.json` and adds `session` (`id` from
`ctx.sessionManager.getSessionId()`, `transcript` from `getSessionFile()`), `integration` (its
version folder name) and `started_at`. it writes the record back only if the file still exists,
so a stopped agent is never re-created. orchestratr records `pid` itself, at launch. then the
extension registers its tools, opens the inbox watch and scans once.

- **not in the factory.** Pi's documentation lets command line extensions take part in its
  `project_trust` event, so their factory can run before the trust question. `session_start`
  comes after it.
- **the negative test.** Pi's `session_start` stayed absent for 45 seconds with a trust dialog
  on screen, and fired 1.2 seconds after the dialog was answered. this was measured on Pi 0.85.1,
  through herdr's Pi integration, which publishes at the same event. over the same period herdr's
  start response, its status and its interactive flag all reported the agent as ready.
- **a message sent before launch** was delivered 1.2 seconds after launch.

### delivery

messages are handed over one at a time, in id order. each becomes one Pi message whose body is
its [`<agent-message>`](/docs/messaging#what-the-model-sees) block.

**busy from the hand-over.** when the extension hands a message to an idle agent, it marks the
agent busy at once, and clears the mark at a real `agent_settled`. while the mark is set, a
message goes as `deliverAs: "steer"` (or `"followUp"`), never as the first prompt, and an
`immediate` aborts. so several steers sent moments apart start one turn, and the rest join it.
the mark does not wait for a turn-start event.

| mode | call |
|---|---|
| wake, at rest | `pi.sendMessage({customType: "agent-message", content, display: true, details: {id}}, {deliverAs: "steer", triggerTurn: true})` |
| first message of a fresh session | `pi.sendUserMessage(content, {deliverAs: "steer"})` |
| `steer` | the same `sendMessage`, with `deliverAs: "steer"`. it reaches the model after the running tool batch, before the next model call. |
| `followUp` | the same `sendMessage`, with `deliverAs: "followUp"`. it runs when the turn has no tool calls and no steers left. |
| `immediate` | at rest, a wake. while working, `ctx.abort()`, then deliver at the first `agent_settled` where `ctx.signal` is unset. |
| empty `immediate` | an interrupt only. it never starts a turn, and is never handed over again. at rest, or when its `sent_at` is more than 10 seconds old as the extension takes it, write `.accepted` and `.delivered` at once and do nothing else, so a stale interrupt never aborts a later turn. while working, `ctx.abort()` and write `.accepted`, then `.delivered` at the first `agent_settled` where `ctx.signal` is unset. |

**check the file first.** before every hand-over, including a re-hand, the extension checks that
`<msgId>.json` still exists. [`orcr agent stop`](/docs/cli#orcr-agent-stop) deletes undelivered
messages before it interrupts, so this check keeps a stop from starting a new turn.

**a watch ending** is a message from `orcr` with a `watch` field. the extension renders it as an
[`<agent-watch>`](/docs/messaging#watches) block, with `<last-text>` and `<screen>` children,
instead of `<agent-message>`. it is handed over like any other message.

**never await the call.** at rest, its promise lasts the whole turn. a call made inside an
`agent_settled` handler is deferred by Pi until the settle ends, so it is safe there.

**why the first message is a user prompt.** a turn started by `triggerTurn` skips
`before_agent_start`, the only place extensions add their per turn system prompt sections. Pi's
base system prompt is still built in 1.0.0. so the first message to a session with no user
message on its branch, at rest, goes as a prompt, and the person's extensions see a normal turn.

| marker | written at |
|---|---|
| `.accepted` | the `sendMessage` or `sendUserMessage` call returns |
| `.delivered` | `message_start` for a message with `role: "custom"` and `customType: "agent-message"`: the id in `details.id`. for the first message, `message_start` for the `role: "user"` message whose text equals the prompt sent. |

measured:

| case | result |
|---|---|
| wake, idle session with history | `.delivered` after 0.9 seconds |
| `steer` during `bash sleep 15` | sent at 6.7 seconds, `.delivered` at 17.6 seconds, when the tool returned. no abort. |
| `followUp` during `sleep 8` | `.delivered` 1.5 seconds after the turn's reply, and answered as its own turn |
| `immediate` during a streaming reply | the reply was cut mid word, and the message was `.delivered` 1 second later |
| `.delivered`, then a provider failure | the marker stays. it means "in context", not "answered". |

### recovery after an interrupt

`ctx.abort()`, and a person's Esc, clear all of Pi's queues. every queued custom steer and
followUp is dropped, from any extension, and never reaches `message_start`. measured: a steer
queued behind `sleep 30`, then an `immediate`. the steer was gone until the extension sent it
again.

the extension keeps a set of every message it handed to Pi that has not reached
`message_start`: steers, and follow-ups that Pi queued itself. after a `/reload`, it rebuilds the
set from the markers on disk: `.accepted` without `.delivered`. at a real `agent_settled`, Pi's
queues are empty, because Pi keeps running while anything is queued. so anything still in the
set was dropped. the extension hands each one over again, in id order and in its own mode, if its
file still exists. the first starts the next turn, and the rest follow the busy rule. a held
`immediate` is not in the set: it is delivered at that same settle, as above. measured: the
dropped steer was handed over again as a steer, together with the `immediate`, and both were
answered.

`ctx.hasPendingMessages()` cannot replace the set: it counts text steers only, not custom
messages.

### tools

`orcr_send`, `orcr_list`, `orcr_read`, `orcr_start` and `orcr_stop`, registered with
`pi.registerTool` at `session_start`, with the parameters in [tools](/docs/integrations#tools).
each one calls the [socket API](/docs/socket-api) (`message.send`, `agent.list`, `agent.read`,
`agent.new`, `agent.stop`) with `from` set to `ORCR_AGENT_ID`. `orcr_send` waits at most 5
seconds for the markers. `orcr_start` returns as soon as the agent is launched, in state
`starting`. a reply to `orcr` is allowed, and the server writes it already delivered.

- **the `orcr_` prefix is required.** two extensions that register one tool name make Pi exit
  with status 1 at startup. measured: an extension that registered `agent_send` beside pi-herd
  killed Pi. pi-herd's tools are `agent_*`.
- **the reply hint names `orcr_send`.** with a hint that named a tool the model also saw from
  pi-herd, the model called pi-herd's `agent_send` first, which failed.
- **the workflow brief goes in `promptGuidelines`** of `orcr_send`. it lands in the base system
  prompt, so turns started by `triggerTurn` have it too.

### dialogs

Pi emits `ui_prompt_start` and `ui_prompt_end` around every extension dialog: `select`,
`confirm`, `input`, `editor` and `custom` (since 0.84.4). the extension turns them into herdr's
own event:

```ts
pi.on("ui_prompt_start", (e) => pi.events.emit("herdr:blocked", { active: true, label: e.title ?? e.kind }));
pi.on("ui_prompt_end", () => pi.events.emit("herdr:blocked", { active: false }));
```

herdr's Pi integration counts these events, so they must pair. Pi already pairs them across
nested dialogs. measured with the bridge:

| dialog | herdr | a message sent meanwhile |
|---|---|---|
| opened by a command, at rest | `blocked` | starts a turn behind the dialog, which stays open. the reply was sent. |
| opened by a `tool_call` hook, mid turn | `blocked` | no `.delivered` while the dialog was open. delivered once it was answered. |

### traps

- **a false `agent_settled`.** it can fire while a run is still going, when a prompt collided
  with it. ignore any settle where `ctx.signal` is set.
- **`/reload`** loads a new copy of the module. keep the taken ids on `globalThis`, close the old
  watch, and on `session_shutdown` release the ids not yet delivered, so the new copy takes them
  again, and rebuild the re-hand set from the markers. measured: a message sent after `/reload`
  was delivered once, with no duplicates. a `/reload` with a message in flight was not measured.
- **a session switch** (`/new`, `/resume`, `/fork`) fires `session_shutdown`, then `session_start`
  with a new id. rewrite `session`. the inbox stays. reading `ctx.signal` on a stale `ctx` can
  throw, so guard it.
- **compaction.** `sendMessage` with `triggerTurn` does not check for a manual `/compact` that is
  running at rest. hold delivery while `!ctx.isIdle() && !ctx.signal`.
- **a prompt that throws before any event.** without credentials, the first prompt threw "No API
  key found": no turn, no `message_start`, no `.delivered`. Pi reports this to the screen only,
  never to an extension. the sender never sees `delivered`. the auth variables of the person's
  launcher must survive the launch line.

## state

| state | source |
|---|---|
| `working`, `idle` | herdr's Pi integration (`~/.pi/agent/extensions/herdr-agent-state.ts`, installed by herdr), pushed from Pi's lifecycle events. herdr does not read the screen for Pi. |
| `blocked` | the orcr extension's bridge, above. |

Pi's own built-in selectors, such as `/model`, `/resume` and `/tree`, do not go through the
extension dialog interface and are not reported. a non-blocking `ctx.ui.custom()` overlay is
reported as `blocked`.

## transcript

```text
$PI_CODING_AGENT_DIR/sessions/<mangled working directory>/<timestamp>_<session id>.jsonl
```

`PI_CODING_AGENT_DIR` defaults to `~/.pi/agent`. the reader finds the file by the glob
`sessions/*/*_<session id>.jsonl`, or takes `session.transcript` from the record. never derive a
working directory from the path: the mangling is lossy. the file appears with the first
assistant message, 1.65 to 3.83 seconds after the first submission (0.85.1).

- **it is a tree.** every entry has an `id` and a `parentId`. after a person moves back with
  `/tree` or forks, the abandoned branch stays in the file, interleaved. read the branch from the
  last entry up through `parentId`, which is what Pi's `buildSessionPath` does.
- **agent messages** are `custom_message` entries with `customType: "agent-message"`. the first
  one in a session is a `role: "user"` message whose text starts with `<agent-message`. show both
  as messages from the sender named in the block.
- **skip** thinking blocks, `toolResult` messages, and entries that are neither `message` nor an
  agent message. an assistant message with `stopReason: "error"` is an error, not an answer.

## session identity

orchestratr chooses the first session id: the agent's id, through `--session-id`. Pi prints
`No project session found with id …; creating a new session with that id.` so the transcript
path is known before launch, and pi-herd, which keys its agents by session id, uses the same id.
`/new`, `/resume` and `/fork` change it later. the extension rewrites `session`, and the inbox
stays at `inbox/<agent id>/`. relaunching with the same `--session-id` resumes the session:
after a kill and a relaunch, only the messages without `.delivered` were delivered again.

## model catalogue

```sh
pi --list-models
```

about two seconds, no billed turn (0.85.1). it is a full startup: it fills the configuration
folder, refreshes the catalogue over the network unless `--offline` is passed, and runs every
extension it discovers. orchestratr runs it with the agents' `PI_CODING_AGENT_DIR`, and without
`ORCR_AGENT_ID`, so the orcr extension stays inert.

thinking levels are per model, and one model accepts only the lowest. the full answer needs one
process per model, so `orcr models` lists the models and whether each supports reasoning, and
asks for levels only for a named model. the model record's thinking level map is an override map
onto provider names, not the allowed values. ask Pi, do not resolve it.

## what is not used, and why

| not used | why |
|---|---|
| `--no-extensions` (`-ne`), or a tool exclusion list | both break the person's setup. `-ne` keeps only `-e` files, and an exclusion list must guess tool names in a person's extensions. |
| `defaultProjectTrust` in `settings.json`, or `trust.json` | a launch argument does the same and writes nothing. |
| `deliverAs: "nextTurn"` | it adds context to the next user prompt and starts no turn. |
| `pi.registerMcpServer` with `orcr mcp` | native tools need no second process, and carry `promptGuidelines`. |
| wrapping `ctx.ui` to see dialogs | Pi already emits `ui_prompt_start` and `ui_prompt_end` for every extension. |
| typing into the pane and matching the transcript | the old design. `message_start` is an exact delivery event, and typing races the person. |

### pi-herd

pi-herd, if the person installed it, also loads in an orcr agent. no flag unloads one package. the
two coexist: different tool names, different folders. pi-herd registers the agent in
`~/.pi/agent/pi-herd/agents/`, so it shows on the person's `/agents` dashboard, and the model also
sees pi-herd's `agent_send`, which reaches pi-herd agents only. future work: pi-herd reads and
writes the shared bus, and becomes the Pi integration.

## not verified

- the negative test with the orcr extension itself on 1.0.0. the evidence is herdr's Pi
  integration on 0.85.1, at the same event.
- `.accepted` timing. the tested extension wrote `.delivered` only.
- the sender's outcome after a prompt that throws: `queued` if `.accepted` was written, `pending`
  if not.
- the compaction guard. it comes from pi-herd's source.
- the empty `immediate`, the 10 second rule, the busy mark and the file check before a
  hand-over. none was in the tested extension. how Pi takes a steer handed over between the wake
  call and the turn's start was not measured.
- a `/reload` while a message is handed over and not delivered, and the rebuild from markers.
- re-handing a dropped follow-up. the measured case dropped a steer.
- tools that call the socket API, and `orcr_read`, `orcr_start`, `orcr_stop`. the tested
  extension had `send` and `list` only, and wrote the bus directly.
- that `--session-id` accepts a UUIDv7. the tests passed a random UUID.
- whether the transcript path changes on resume, and every transcript entry type not named above.
- the 0.84.4 floor, where `ui_prompt_*` arrived. the tests ran on 1.0.0 only.
- that the factory runs before the trust question. it is inferred from Pi's documentation.
- the command that lists the thinking levels for one model.
