---
title: "sending without typing"
description: "handing a message to an agent directly, on the two kinds that allow it"
---

today orchestratr pastes text into the composer, presses enter, and then confirms delivery by
reading the delivery record (see [delivery](/docs/readiness-and-delivery#delivery)). two of the
four kinds can instead be handed a message directly. that call replaces both the keystrokes and
the inference, and it returns the outcome.

## what exists today

| kind | mechanism | needs orchestratr code inside the agent |
|---|---|---|
| OpenCode | `POST /session/{id}/message` on the port orchestratr already pins at launch | no |
| Pi | an extension calling the agent's own send function, loaded with `-e` | yes |
| Codex | `codex queue`, only when a daemon holds the thread | no, but conditional |
| Claude Code | none usable | not applicable |

### OpenCode

the cleanest case. orchestratr already pins an HTTP port at launch, for readiness and for the
blocked check (see [OpenCode pinned port](/docs/agents/opencode#the-pinned-port)), so sending becomes one more
request on a connection that already exists.

the session id must come from the agent's own session-selected event. never guess it.

the same request also accepts a `variant`. that is the only way to change effort partway
through a session without a person pressing keys. verified: it took effect in an environment
where the configuration route had deliberately been left inert, so the effect came from the
request alone.

<Callout type="warn" title="do not deliver through the TUI endpoints">
do not use `/tui/append-prompt` and `/tui/submit-prompt` for delivery. they return success
unconditionally and do nothing when the composer is not focused, so they offer the ergonomics of
an interface with all the uncertainty of a keystroke. they are usable for the
[readiness round trip](/docs/agents/opencode#readiness) only because that check waits for the
text to come back out.
</Callout>

### Pi

Pi exposes a send function to extensions, with a choice of delivering the message as a steer or
as a follow-up. that function can fix Pi's worst property: today a message sent mid turn is not
confirmed until the running tool call finishes, which is unbounded (see
[Pi delivery](/docs/agents/pi#delivery)).

it requires shipping an extension, which orchestratr does not do. see
[shipping our own hooks, plugins or extensions](/docs/future/dropped#shipping-our-own-hooks-plugins-or-extensions)
for that decision. if orchestratr ever ships one, this is the strongest reason.

### Codex

`codex queue` reaches a thread that a running app server daemon has loaded. orchestratr does
not run that daemon and does not speak its protocol, so this is only an opportunistic fast path,
taken when the daemon happens to exist and to hold the thread. it is not a foundation to build
on.

### Claude Code

a cross-session inbox over a local socket does reach the running interactive session. it is key
authenticated, undocumented, versioned, and has no command line client. revisit it only if a
supported command appears.

## why the first version types instead

typing works on all four kinds, with one code path. every kind already confirms delivery from
its own delivery record, three of them in under half a second, so the uncertainty an interface
could remove is already small.

adopting interface delivery for two kinds means two send implementations behind one interface,
for a gain that matters most on the kind where it is hardest to get.

## what it would buy

- no composer clearing, no bracketed paste, no enter key, and no enter retry.
- no risk of typed text being consumed by a dialog and answering it.
- `possibly_delivered` becomes rare or impossible for those kinds, because the call returns a
  result instead of leaving orchestratr to infer one (see
  [confirmation](/docs/cli#confirmation)).
- for Pi specifically, the unbounded mid turn confirmation wait disappears.

## what it would cost

- two send paths to maintain and test instead of one.
- a second control plane per kind, versioned separately from the terminal.
- a new failure mode: a message that reaches a different session from the one shown in the
  pane. any implementation must prove that it targets the session the person can see, and must
  fail rather than create a parallel session.

## the evidence

a project that solves the same problem across 13 agents delivers every interactive message as a
paste plus a separate enter. it never attempted interface delivery.

that does not prove interface delivery is wrong. it is a reason to treat it as an improvement to
prove, not as the obvious thing everyone does.
