title: "Dropped items"
description: "cuts and reasons"
---

Each item here was considered and left out.

## Per-kind interrupt-and-send shortcuts

Two kinds offer a single key that interrupts the current turn and submits a pending message
at the same time. Both were verified to work. Both are better than the general sequence:
one key instead of four steps, no polling, and on one of them the risky second Escape
becomes structurally impossible because the pending message consumes it.

Cut because the general sequence reaches the same end state on every kind. Two extra code
paths to save about two seconds, on a command a person types, is not a trade worth making
before the general path has been used in real work.

## Shipping our own hooks, plugins or extensions

orcr installs no code that runs inside an agent. This was reconsidered against a project that
ships such integrations, and the evidence closed it.

What their integrations report is a closed list of 19 fields covering session start and end,
turn start and stop, and one tool event. None of them reports a pending approval or a pending
question. Approvals and questions are read off the screen, despite every one of those hooks
being installed.

So the value is one thing: binding a pane to the agent's own session identifier without
guessing. The backend already supplies that for three of our four kinds. Where it fails for
the fourth, the cause is a backend defect that an orcr hook cannot fix, because the
integration already loads and reports correctly and the report is discarded.

Three further reasons not to:

- A hook on a tool-use event is dangerous as an approval channel. On one agent an empty
  response reads as a denial, and on another that event fails closed. An orcr hook that
  crashes stops a person's agent running anything.
- Installing a hook means editing configuration that the person and other tools also write.
  The project studied here needs four separate strategies to avoid clobbering, and records a
  scar where a stale block silently won.
- Where the backend already installs its own integration on the same event, an orcr hook is
  the second one on it.

One pattern applies if the situation changes: where an agent has a plugin API and writes no
transcript, the right shape is a plugin that writes the transcript, which orcr then tails.
None of the four kinds is in that position.

## Classifying why an agent is blocked

An earlier design classified the reason an agent was blocked, so that a caller can tell a
permission prompt from a plan review from a trust dialog.

Cut because the backend reports that an agent is blocked but gives no structured reason.
Producing one means screen reading, interpreted per kind, which is the most fragile thing
orcr can own. orcr reports that an agent is blocked and passes through
whatever text the backend already provides.

## An abstract effort vocabulary

A shared set of effort values, such as low, medium and high, mapped onto each kind's own
words.

Cut because the words do not line up. Of seven effort words across the four kinds, four
appear on only one or two kinds, and two kinds spell the same idea differently. Any mapping
has to guess, and a wrong guess changes what a turn costs. `--effort` passes through as
written, and `orcr models` shows what each kind accepts.

## Catalogue caching

A cache file, invalidated on the agent binary version with a time backstop and a short
negative cache for failed probes.

Cut because the probes run in parallel and finish in about thirty seconds, on a command a
person runs deliberately. The cache costs an invalidation policy, a staleness question and a
partial-answer flag.

## A separate identifier for each agent

A generated id alongside the human readable name.

Cut because the backend already requires names to be unique within a session, and orcr uses
one session. A second identifier adds a translation table and nothing else.

## Message queueing in orcr

Holding a message in orcr while an agent is busy, and submitting it when the agent frees up.

Cut because every kind already queues natively and delivers at the next tool call. Building a
second queue on top of a working one adds a place for messages to be lost, and makes it
unclear which queue a caller is talking to.

## Other command surface cuts

| Cut | Reason |
|---|---|
| Separate `cat`, `head`, `tail` and `less` commands | One `read` command with `--last` and `--follow` covers all four. |
| A repeatable kind filter | One kind at a time is enough, and the shell can loop. |
| Markdown and JSON transcript formats | Text for people, JSONL for programs. Two formats, two audiences. |
| Content search across transcripts | Standard tools search JSONL output better than a flag would. |
| Output redaction | A half-working filter invites trust it cannot earn. |
| Truncation controls on tool summaries | The text format summarises tool calls in one line already. |
| A dry run mode | The commands that change things are small enough to read. |
| A time to live on agents | Nothing was going to enforce it. |
