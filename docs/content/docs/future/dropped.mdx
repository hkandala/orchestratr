---
title: "dropped items"
description: "smaller items considered for the first version and cut, with the reason for each"
---

each item on this page was considered and left out.

## per-kind interrupt-and-send shortcuts

two kinds offer a single key that interrupts the current turn and submits a pending message at
the same time. both were verified to work, and both beat the general sequence: one key instead
of four steps, no polling, and on one of them the risky second escape becomes structurally
impossible, because the pending message consumes it.

cut because the general sequence (see [`orcr agent message`](/docs/cli#orcr-agent-message) with
`--immediate`) reaches the same end state on every kind. two extra code paths to save about two
seconds, on a command a person types, is not worth it before the general path has been used in
real work.

## shipping our own hooks, plugins or extensions

orchestratr installs no code that runs inside an agent. this was reconsidered against a project
that ships such integrations, and the evidence settled it.

that project's integrations report a closed list of 19 fields, covering session start and end,
turn start and stop, and one tool event. none of them reports a pending approval or a pending
question. approvals and questions are read off the screen, even with every one of those hooks
installed.

so the value is one thing: binding a pane to the agent's own session id without guessing. the
backend already supplies that for three of the four kinds. where it fails for the fourth
(OpenCode, see [session identity](/docs/agents/opencode#session-identity)), the cause is a
backend defect that an orchestratr hook cannot fix: the integration already loads and reports
correctly, and the backend discards the report.

three further reasons not to:

- a hook on a tool-use event is dangerous as an approval channel. on one agent an empty
  response reads as a denial, and on another that event fails closed. an orchestratr hook that
  crashes stops a person's agent from running anything.
- installing a hook means editing configuration that the person and other tools also write. the
  project studied here needs four separate strategies to avoid clobbering, and records a scar
  where a stale block silently won.
- where the backend already installs its own integration on the same event, an orchestratr hook
  would be the second one on it.

one pattern applies if the situation changes. where an agent has a plugin API and writes no
transcript, the right shape is a plugin that writes the transcript, which orchestratr then
tails. none of the four kinds is in that position.

## classifying why an agent is blocked

an earlier design classified the reason an agent was blocked, so that a caller could tell a
permission prompt from a plan review from a trust dialog.

cut because the backend reports that an agent is blocked but gives no structured reason.
producing one means screen reading, interpreted per kind, which is the most fragile thing
orchestratr could own. orchestratr reports that an agent is blocked and passes through whatever
text the backend already provides (see [kind adapter](/docs/implementation#kind-adapter)).

## an abstract effort vocabulary

a shared set of effort values, such as low, medium and high, mapped onto each kind's own words.

cut because the words do not line up. of seven effort words across the four kinds, four appear
on only one or two kinds, and two kinds spell the same idea differently. any mapping has to
guess, and a wrong guess changes what a turn costs. `--effort` passes through as written, and
[`orcr models`](/docs/cli#orcr-models) shows what each kind accepts.

## catalogue caching

a cache file, invalidated on the agent binary version, with a time backstop and a short
negative cache for failed probes.

cut because the probes run in parallel and finish in about 30 seconds, on a command a person
runs deliberately. the cache would cost an invalidation policy, a staleness question and a
partial-answer flag.

## a separate identifier for each agent

a generated id alongside the human readable name.

cut because the backend already requires names to be unique within a session, and orchestratr
uses one session. a second identifier adds a translation table and nothing else.

## message queueing in orchestratr

holding a message in orchestratr while an agent is busy, and submitting it when the agent frees
up.

cut because every kind already queues natively and delivers at the next tool call (see
steering on each [agent page](/docs/agents)). a second queue on top of a working
one adds a place for messages to get lost, and makes it unclear which queue a caller is talking
to.

## other command surface cuts

| cut | reason |
|---|---|
| separate `cat`, `head`, `tail` and `less` commands | one `read` command with `--last` and `--follow` covers all four. |
| a repeatable kind filter | one kind at a time is enough, and the shell can loop. |
| markdown and JSON transcript formats | text for people, JSONL for programs. two formats, two audiences. |
| content search across transcripts | standard tools search JSONL output better than a flag would. |
| output redaction | a half-working filter invites trust it cannot earn. |
| truncation controls on tool summaries | the text format already summarizes each tool call in one line. |
| a dry run mode | the commands that change things are small enough to read. |
| a time to live on agents | nothing was going to enforce it. |
