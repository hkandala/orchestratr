## the interface

OpenCode differs from the other three kinds in shape, not only in protocol.

```sh
opencode serve --port <n>
```

this starts one HTTP server that serves every session. the other three kinds run one process per
agent, so a supervisor here manages one long lived server plus n logical sessions, rather than n
processes.

sessions are created and driven over HTTP. events arrive on a server sent event stream. the
stream has an event cursor, so a controlling program that reconnects can resume rather than lose
events.

there is also an ACP interface:

```sh
opencode acp
```

ACP session creation returns the flattened model list, where each entry is the exact string the
model argument accepts, including the effort variant. verified: its startup took about twenty
seconds, against about half a second for the fast paths of the other kinds.

## model catalogue

[OpenCode model catalogue](/docs/agents/opencode#model-catalogue) records where the catalogue
comes from for this kind, and why it needs a server.

## state

the server reports session status and a separate asked-permission event. those are the
structured forms of `working` and `blocked`.

## transcript

storage is a SQLite database at `$XDG_DATA_HOME/opencode/opencode.db`, with write ahead logging.
`opencode export <session-id>` renders one session.

verified in interactive mode: a message submitted in the middle of a turn is recorded at submit
time, not at turn end. the recorded time was 50.8 seconds before a running 60 second tool
returned.

## builds

a binary named `opencode` is not always OpenCode (see
[OpenCode version requirement](/docs/agents/opencode#version-requirement)), so any work here must first check
`opencode --version` against upstream.

## not verified

- whether the HTTP event stream and the database agree on ordering under load.
- whether an invalid effort variant fails at launch or silently starts the base model.
