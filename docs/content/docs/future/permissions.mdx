orchestratr starts every agent with permissions fully bypassed (see
[scope](/docs/purpose#scope)). this page records what should replace permission bypass, and
why orchestratr cannot make that change yet.

## the intended default: each kind's auto mode

an auto mode is a middle setting between asking about every action and checking nothing.

| kind | full bypass | auto mode | does the auto mode ever ask? |
|---|---|---|---|
| Claude Code | `--dangerously-skip-permissions` | `--permission-mode auto` | yes, measured |
| Codex | `--yolo` | `--approve-for-me` | probably, not provoked |
| OpenCode | `--yolo` | `--auto` | no such mode exists |
| Pi | permissive by default | none | no such mode exists |

where an auto mode exists, it is the better choice. it keeps the agent's own safety checks on
risky actions. on at least one kind, the bypass flag also turns off a sandbox that the auto
mode keeps. so bypass is more permissive, and it also removes a containment boundary.

each project documents its bypass flag as appropriate for machines that something else already
sandboxes. orchestratr sandboxes nothing.

so the auto mode is the right default for the kinds that have one, once orchestratr can answer
a dialog. two of the four kinds have one.

## what the measurements showed

**Claude Code's auto mode asks, but only after a while.** all nine graded requests passed
silently, including a write to an absolute path outside the workspace, which the classifier
reviewed and allowed. escalation is not per action. after three consecutive classifier denials
in one session, a blocking dialog appears that reads `Auto mode classifier requires
confirmation for this command`. it does not time out: it was still blocking after 172 seconds.
there is a second limit at 20 denials in a session, and a third path when the classifier's
own transcript outgrows its context window.

a short test says the mode never asks. a long-running agent, which is what orchestratr is
for, eventually hits a counter and stops.

**Claude Code's `dontAsk` is not the answer.** it reads like a mode that never prompts. the
shipped bundle defines it as `Don't prompt for permissions, deny if not pre-approved`. it does
not ask; it refuses. an agent whose tool calls are silently denied fails at its work instead of
stalling.

**OpenCode has no intermediate mode.** `--auto`, `--yolo` and `--dangerously-skip-permissions`
are three spellings of one boolean, combined into a single value. there is nothing between
asking and not asking (see [OpenCode permissions](/docs/agents/opencode#permissions)).

**Pi has no intermediate mode either.** it is permissive and offers no gradation.

so this work applies to Claude Code and Codex. for the other two there is nothing to switch to.

## why orchestratr cannot use them yet

an auto mode approves routine actions and stops to ask about risky ones. stopping to ask is the
problem.

orchestratr has no command to approve or reject anything. an agent that stops to ask sits in
its pane until a person opens that pane by hand and answers. nothing in orchestratr can clear
it, and on one kind nothing in orchestratr can even report that it happened (see
[Pi state](/docs/agents/pi#state)).

using an auto mode without an approve command would therefore require a per-agent screen
reader, which is the one thing orchestratr has decided not to own.

## what has to be built first

in this order:

<Steps>
<Step>

**report a waiting agent accurately.** a caller must be able to see that an agent stopped to
ask, and what it asked. until then, an auto mode turns a working agent into a silent stall.

</Step>
<Step>

**answer from orchestratr.** a command that approves or rejects the pending request, and a
socket method behind it. without this, reporting can only tell a person to answer by hand.

</Step>
<Step>

**switch the default,** per kind, to the auto mode.

</Step>
</Steps>

the first step is the hard one, and it is not uniform across kinds:

- one kind reports a waiting state in a file it already writes.
- one exposes a pending request over a local HTTP endpoint.
- one carries typed waiting states in a protocol orchestratr does not currently speak.
- one reports nothing at all.

[limitations](/docs/limitations#scope) lists which kind is which.

## Pi

if Pi has no graduated mode, it keeps its current behavior after this work lands. orchestratr
should say so, rather than imply that one permissions setting covers all four kinds equally.

## what not to do

<Callout type="warn" title="do not approve by typing into a matched screen">
do not add an approve command that works by sending keystrokes to a screen orchestratr has
matched against a pattern. that is the screen reading this design exists to avoid, and it fails
in the worst possible direction: pressing the wrong row answers a question that a person was
about to answer differently.
</Callout>

an approve command should use the same class of signal the rest of orchestratr uses (see
[readiness, delivery, and state](/docs/readiness-and-delivery)). where a kind offers no such
signal, orchestratr should refuse to answer for that kind and say why.
