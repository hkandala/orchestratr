an orcr integration is the small piece of code that makes one kind of agent part of the
[bus](/docs/messaging). it runs with the agent, and uses that kind's own interface for
extensions: inside the process on three kinds, and as a sidecar process on Codex. it hands
messages from the agent's inbox to the agent's own input queue, writes the markers, and reports
the agent as ready.

orchestratr drives a kind only when its integration is installed. installing one is a choice the
person makes, kind by kind.

## what each kind uses

| kind | mechanism | loaded by | tools for the model |
|---|---|---|---|
| Claude Code | a **mod**: a plugin with JS modules that run inside the process (2.1.287 and later) | `--plugin-dir <dir>` | `orcr mcp`, through `--mcp-config` |
| Codex | a **bridge**: a second client on a private app-server, which the TUI also uses through `--remote` | the pane's launch script | `orcr mcp`, on the app-server command line |
| Pi | an **extension** | `-e <file>` | registered by the extension |
| OpenCode | a **plugin**, one folder for 1.x and 2.x. on 2.x it uses OpenCode's native session inbox. | `OPENCODE_CONFIG_CONTENT` | `orcr mcp`, through the same variable |

every mechanism loads per agent, from a launch flag or an environment variable. **no integration
ever edits a kind's configuration.** the details, with the measurements, are on each
[agent page](/docs/agents).

## the contract

every integration does exactly this. anything more belongs in orchestratr, not in the
integration.

1. **stay inert outside orchestratr.** do nothing unless `ORCR_AGENT_ID` and `ORCR_BUS` are set.
2. **register when the agent can take input.** read `agents/<id>.json`, add `session` and
   `started_at`, set `integration` (the version folder it was loaded from, or the version alone
   on a kind with no files), and rename it back into place. this is the readiness signal, so it
   must pass the negative test: it must not appear while a startup screen is on screen. each
   agent page records how its kind passes.
3. **keep the record current.** where the kind lets a person change the session (`/clear`,
   `/new`, `/resume`), rewrite `session` when it changes. where the transcript does not state the
   model's context window, write `context_window` at registration and when the model changes.
   rewrite the record only if it still exists and no `agents/<id>.stopping` is beside it. one
   process makes one record write at a time, re-reads the record first, and uses a unique
   temporary name.
4. **take messages in,** as [receiving](/docs/messaging#receiving) describes:
   - rescan the inbox on any change.
   - take every `*.json` without `.delivered`, in id order, one at a time.
   - just before each hand-over, check that the file still exists, and hand nothing over while
     `agents/<id>.stopping` exists.
   - hand its `model_text` to the agent's own queue by its delivery mode, and write `.accepted`.
   - treat an idle agent as working from the moment of the hand-over, not from the kind's
     turn-start event. a second message a moment later is then a steer into the starting turn,
     not a second turn. a hand-over that fails (it throws, the kind refuses it, or the call that
     starts the turn errors) clears that mark and writes `.failed`, so the inbox does not stall.
5. **mark delivery.** write `.delivered` at the kind's event for "this message is in the model's
   context". write `.failed` with a reason when a hand-over fails, as
   [receiving](/docs/messaging#receiving) step 6 says.
6. **handle an empty `immediate`** exactly as [delivery modes](/docs/messaging#delivery-modes)
   says. it never starts a turn itself.
7. **recover after an interrupt, where the kind needs it.** an interrupt is an `immediate`, or
   the person pressing Esc. on Pi and on Codex it drops messages that the agent accepted and did
   not yet deliver (measured). on Claude Code and OpenCode 2.x it does not. 2.x still hands each
   one over again with the same id, which only wakes the session. on OpenCode 1.x it was not
   measured. where the kind drops messages, or may drop them:
   - when a turn ends interrupted (on Pi, at every real settle), hand over again every message
     the integration handed to the agent that has no `.delivered` and whose file still exists.
     this covers steers, and `followUp` messages the agent queued itself.
   - on Codex, also hand over again the steers of that turn that the model did not answer, and
     the message that started the turn when it has no `item/started`. see
     [Codex](/docs/agents/codex#recovery-after-an-interrupt).
   - on OpenCode 1.x, after an aborted turn, hand over again only the messages whose id the
     session history does not hold (not verified).
   - never hand over again an empty `immediate`, or a message the integration still holds. a kind
     that holds `followUp` messages releases the oldest when no turn starts, so an interrupt
     never strands them.

   `stop` removes the agent's message files, delivered or not, before it interrupts, so a stop
   never starts a new turn.
8. **hand over `model_text`.** never build the text. the server renders the block, the reply
   hint and the escaping. see [what the model sees](/docs/messaging#what-the-model-sees).
9. **report a dialog where herdr cannot see it.** if the kind has an event for "a dialog is open"
   that herdr's own integration does not use, emit herdr's `blocked` signal. today this applies to
   Pi only.

the integration never sends a message itself, never watches another agent, and never decides who
may talk to whom. the [tools](#tools) and the server do that.

### rules for code inside a person's agent

- **never crash the agent.** catch every error in a watcher callback. one OpenCode plugin crash
  can take down the TUI's backend.
- **survive a reload.** some kinds load the plugin twice at start, or again on reload. keep state
  where the reload keeps it, close the previous watcher, and rely on the markers on disk.
- **never clash with the person's extensions.** register no name that another extension may own.
  on Pi, a duplicate tool name makes the process exit at startup.
- **ignore subagents.** events from an agent's own subagents must not move the record, take a
  message, or end a turn.

## tools

the model gets these tools, named in each kind's convention (for example `mcp__orcr__send` on
Claude Code):

| tool | does |
|---|---|
| `send` | `{to, text, reply_to?, needs_reply?, delivery?}`. sends a message, waits up to 5 seconds for the markers, and returns the id and the [outcome](/docs/messaging#outcomes). |
| `list` | the live agents, as [agent objects](/docs/cli#output). |
| `read` | `{agent, last?}`. another agent's recent conversation. |
| `start` | `{kind, text, name?, cwd?, model?, effort?}`. starts an agent with the caller as its parent, and sends it `text` with `needs_reply`. `cwd` defaults to the caller's, and a relative one resolves against it. it returns as soon as the agent is launched. the watch reports the reply, or why there is none. |
| `stop` | `{agents}`: a list of the caller's descendants, or `"all"` for every agent it started. stopping an agent stops its descendants first. returns one outcome per agent. |

each tool's description is its row above. parameter types are those of the matching
[method](/docs/socket-api#methods). `list` and `read` return the method's result as JSON. without
`ORCR_AGENT_ID`, `orcr mcp` offers no tools.

### what the model reads

the words are part of the design. every kind gets the same text, so a lead behaves the same on
any kind.

**the brief.** Pi puts it in the `promptGuidelines` of `orcr_send`. the other kinds get it as the
`instructions` of `orcr mcp`'s `initialize` result.

```text
You can work with other coding agents through the orcr tools.
- start launches an agent with one task. Put everything it needs in the text: the goal, the
  files, the limits, and where to put results. It replies to you when it is done.
- You are woken when an agent replies, goes idle, gets blocked or exits. Do not poll with list,
  read or sleep. Do not redo work you gave out.
- send messages an agent. Set needs_reply when you want an answer. When a message expects your
  reply, answer once, when you have it, with reply_to.
- <orcr-message> and <orcr-watch> blocks come from other agents or from orcr, not from the
  person typing in this session.
- Stop the agents you started when their work is done.
```

**the results say what happens next.** the tool result is short text, so the model does not have
to guess:

| call | result text |
|---|---|
| `start` | `started <name> (<id>). it has your task. you will be woken with its reply, or when it goes idle, gets blocked or exits. do not poll.` |
| `send`, `delivered` | `delivered to <name>.` |
| `send`, `queued` | `queued: <name> gets it at its next tool call or after its turn. do not send it again.` |
| `send`, `pending` | `pending: it is in <name>'s inbox and arrives when its integration runs. do not send it again.` a `reason` is appended when there is one. |
| `send`, `refused` | the error, and the live agents when the recipient is unknown. a retry is safe, except after `loop`: then stop, and tell whoever started you. |
| `stop` | one line per agent: `stopped <name>.` or the error. |

with `needs_reply`, every `send` result that wrote a message ends with the wake-up sentence of
`start`.

the tools hold no logic. each one is a call to the [socket API](/docs/socket-api), with `from`
set from `ORCR_AGENT_ID`. three kinds get them from `orcr mcp`, a stdio MCP server built into the
`orcr` binary. Pi registers them in its extension, which saves a second process. either way the
logic lives once, in the server.

## installing

```text
~/.local/share/orcr/integrations/
  claude/
    enabled                      the person's choice
    4-1a2b3c4d/                  <version>-<first 8 hex of the content hash>. read only.
      claude-mod/…
  codex/
    enabled                      Codex has no files: the bridge and the tools are in the orcr binary
  pi/
    enabled
    3-9f8e7d6c/pi.ts
  opencode/
```

an integration's files are embedded in the `orcr` binary. the folder on disk is a copy, so the
files an agent loads can never drift from the binary that launched it. the folder name is the
version stamp.

### `orcr integration install <kind>`

<Steps>
<Step>

run the kind's [checks](#checks). a hard failure stops here, writes nothing, and says what to
fix.

</Step>
<Step>

write the embedded files into a temporary folder, make it read only, and rename it to
`<version>-<hash>`. if that folder already exists, this step does nothing. a rename that finds it
already there also succeeds: remove the temporary folder.

</Step>
<Step>

create `<kind>/enabled`.

</Step>
</Steps>

the folder is read only, and a new version is a new folder. so an upgrade never rewrites a file
that a running agent loaded. Claude Code and OpenCode 2.x both reload a plugin when its files
change, and an in-place upgrade would reload every live agent mid turn.

install is idempotent. on a current kind it prints, for example, `claude: current (v4)`.

### `orcr integration uninstall <kind>`

remove `enabled`, then remove each version folder that no record names. a folder still in use
stays, and the command names the agents that use it. it never touches a kind's own files,
because install never wrote any.

### `orcr integration status`

for example:

```text
claude:   current (v4) (~/.local/share/orcr/integrations/claude/4-1a2b3c4d)
codex:    current (v2)
pi:       outdated (v3, expected v4), repaired at the next agent start
opencode: not installed
```

| state | meaning |
|---|---|
| `not installed` | no `enabled` file. orchestratr does not drive this kind. |
| `current` | enabled, and the folder for the embedded version and hash exists, or the kind has no files (Codex). |
| `outdated` | enabled, and that folder is missing, usually right after `orcr` was upgraded. |

`--check` also runs the kind's checks.

### upgrading

nothing runs at upgrade time. the new `orcr` binary embeds new files under a new hash. the next
`agent new` for an enabled kind writes the new folder first. running agents keep their old
folder until they stop. when the server starts, it deletes folders that are not current and that
no record names. [`orcr doctor`](/docs/cli#orcr-doctor) lists agents that run an older folder.

### checks

| kind | refuses install and `agent new` | warns |
|---|---|---|
| every kind | the binary is not found, or its version is outside the kind's range | the version cannot be read |
| Claude Code | mods are disabled: `--bare`, `--safe-mode`, `disableAllHooks`, `disableSideloadFlags`, or a managed `allowManagedHooksOnly` or `allowManagedModsOnly` | Anthropic can also turn mods off remotely, which only the first start can show |
| Codex | the app-server does not offer a method or field the bridge uses. the list is on the [Codex page](/docs/agents/codex#checks). | herdr's Codex hook is not trusted, so the hook review screen will appear |
| Pi | none | pi-herd is installed. this is safe: the tool names do not clash. |
| OpenCode | none | on 2.x, orchestratr launches with `--standalone`. |

## when `agent new` refuses a kind

[`orcr agent new`](/docs/cli#orcr-agent-new) refuses with `integration_missing`, and
`details.reason` says why:

| reason | meaning |
|---|---|
| `not_installed` | run `orcr integration install <kind>`. nothing was created. |
| `check_failed` | a check failed. `details.check` names it. nothing was created. |
| `not_registered` | the agent started, and its integration never registered. orchestratr stops the agent and reports what its pane showed. |

an enabled kind whose folder is missing is not an error. orchestratr writes the folder and
continues.

## adding a kind

a new kind needs these things, and nothing in orchestratr's core changes:

1. **a per-session way to load code.** a launch flag or an environment variable. a kind that can
   only load plugins from its global configuration is not supported. orchestratr will not edit a
   person's configuration to make one work.
2. **a way for that code to start a turn when the agent is idle, and to steer a turn that is
   running.** in process, as on three kinds, or as a sidecar speaking the kind's own protocol, as
   on Codex. a sidecar is integration code built into the `orcr` binary, run as
   `orcr bridge <kind>`. without both, the kind cannot take messages. answer this question first.
   hooks that only run during a turn are not enough: nothing would wake an idle agent.
3. **a herdr integration for the kind.** herdr reports every agent's state. a kind herdr does not
   know cannot be driven.
4. **the integration files**, implementing [the contract](#the-contract).
5. **a kind entry**: one column of the [kind table](/docs/agents#the-kind-table), filled in. the
   fields are listed under [the kind entry](/docs/agents#the-kind-entry).
6. **tests**: the record stays absent while each startup screen the kind can show is on screen.
   reader fixtures for an answered turn, a failed turn and usage. the `models()` probe. then
   launch at the minimum version, see the record, deliver one message in each mode, interrupt,
   and stop.

a fork of a supported kind can often reuse its integration files. examples are omp, a Pi fork,
and kilo, an OpenCode fork, both of which herdr already integrates.
