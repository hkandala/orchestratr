## what orchestratr is

orchestratr starts AI coding agents, drives them, and reports on them. it supports four kinds:

- Claude Code
- Codex
- Pi
- OpenCode

every agent runs as an interactive terminal program inside a herdr pane. orchestratr gives it
an identity, tracks its state, and offers one set of commands that works the same way for all
four kinds.

the [socket API](/docs/socket-api) is the product. the [`orcr` command line tool](/docs/cli)
is one caller of it. any program that can open a UNIX socket and write a line of JSON can do
everything the command line tool can do.

## the problem

a coding agent runs alone: one terminal, one agent, one person watching it.

real work needs more than one agent:

- a reviewer per concern
- a worker under a verifier
- a nightly job that triages issues

that work often needs agents of different kinds, because each kind has different strengths
and its own subscription quota.

## why interactive sessions

every kind can also run without a terminal. orchestratr does not use that mode, because
interactive sessions keep three properties that matter at this scale.

1. **price.** an interactive session bills against a flat subscription plan. a
   non-interactive call bills per token. across many agents, this difference sets the total
   cost.
2. **control.** a person can watch an interactive session while it works, correct it mid
   turn, and take over the terminal when it goes wrong.
3. **one interface.** each kind has a different non-interactive mode, with different flags
   and different output. the interactive terminal is the one surface all four kinds share.

[headless](/docs/future/headless) records what the non-interactive modes would offer and why
they are future work.

## what orchestratr provides

| capability | what it means |
|---|---|
| identity | every agent gets a stable name and id that survive a restart. |
| placement | agents that share a working directory share a workspace. |
| lifecycle | start an agent, send it a message, interrupt it, attach to it, stop it. |
| state | one state vocabulary for all four kinds. |
| transcripts | read the conversation of any agent in one format. |
| catalogue | list the models and effort values each kind accepts. |

## scope

orchestratr controls only the agents it starts. it does not adopt agents that another tool
started. see [external agents](/docs/future/external-agents).

orchestratr starts every agent with permission prompts turned off. an agent it starts can run
any command in its working directory without asking. this is deliberate, and orchestratr
offers no command to approve or reject a single action. see
[permissions](/docs/future/permissions) for what would replace this.

herdr is the terminal backend. orchestratr requires herdr, and it requires the herdr
integration for each kind it drives.

## design rules

these rules settle design arguments. read them before proposing a change.

1. **one behavior for all kinds.** where the agents differ, orchestratr hides the difference
   or states it. it does not grow a separate code path for each kind.
2. **per-kind knowledge is data, not code.** launch arguments and startup steps live in a
   table.
3. **do not reimplement herdr.** if herdr answers a question, orchestratr asks herdr.
4. **fail closed.** when orchestratr cannot confirm that an action is safe, it refuses and
   says why.
5. **the socket API comes first.** a command line feature that the API cannot express is a
   bug in the API.
6. **say what is not known.** an honest gap is more useful than a confident guess.
