orchestratr holds no screen patterns and maintains no screen matching code.

the backend derives some of its state by reading the terminal, under per-kind rules that it
maintains and updates. readiness and delivery both come from files the agent writes instead,
because the terminal cannot be trusted for either. [limitations](/docs/limitations)
records the measured failures.

so orchestratr answers three questions from the agent's own files. before any of that, it
removes the things that can make an agent stop and wait.

## remove what can stall

an agent stops and waits for a person in three ways. orchestratr removes all three before
launch, rather than detecting them afterwards.

1. **a startup screen.** see [startup screens](#startup-screens).
2. **a tool whose job is to ask the person something.** every kind can be told not to load
   these. the exact names and syntax are under startup on each [agent page](/docs/agents).
3. **a program that the agent starts inside a shell command, and that waits for input of its
   own:**
   - an interactive rebase
   - a pager
   - a host key confirmation
   - a login dialog

### the shared environment

the third way is the same for every kind, so orchestratr handles it once, in the environment it
gives every agent:

```sh
EDITOR=true  VISUAL=true  GIT_EDITOR=true
PAGER=cat    GIT_PAGER=cat
GIT_TERMINAL_PROMPT=0  CI=1
```

without this, an agent can stall inside a shell command that orchestratr cannot see. that is
worse than a dialog, because no state reports it.

`VISUAL` is not optional. it takes precedence over `EDITOR` in most editor selection, and
leaving it out was proven to hand a real editor the terminal on one kind despite
`EDITOR=true`. `GIT_PAGER` is set separately from `PAGER` for the same reason.

<Callout type="warn" title="the environment is not always enough">
  one kind, Codex, captures a shell snapshot at startup and applies it after orchestratr's
  environment, which silently defeats `EDITOR`. for Codex, orchestratr also sets these values
  through the agent's own configuration. see [Codex startup](/docs/agents/codex#startup).
</Callout>

### startup screens

every kind shows at least one screen before it accepts input, and permission bypass removes
none of them. each screen has a configuration key or a launch argument that stops it from
appearing.

orchestratr sets those before it launches the agent. a screen that never appears needs no
detection and no keystroke.

three of the four kinds carry every startup setting as a launch argument or as inline
configuration, so orchestratr writes no file for them.

Claude Code is the exception. three of its keys have no launch form, so orchestratr writes them
to the person's configuration: the folder trust record, and two keys that clear the theme
picker and the security notes screen. it writes a key only when the key is absent, and writes
the trust key only for the working directory. the result is the state that answering the
dialogs once produces. see [Claude Code startup](/docs/agents/claude#startup).

the write must follow a symbolic link, so orchestratr resolves the real path first and writes
there. the rules for that write are in
[writing a person's configuration](/docs/implementation#writing-a-persons-configuration).

when orchestratr cannot set a key, [`orcr agent new`](/docs/cli#orcr-agent-new) fails before
launching. it does not start an agent that will stop on a dialog.

## readiness

each kind has a signal that appears only after every startup screen is cleared, and
orchestratr waits for that signal. on three kinds it is a file the agent writes. on Pi it is
the session reference that the herdr integration for Pi publishes.

what makes a signal trustworthy is the negative test: a signal is usable only if it stays
absent while a dialog is on screen. several obvious candidates fail that test by more than a
minute.

| kind | readiness signal |
|---|---|
| Claude Code | [status file](/docs/agents/claude#readiness) |
| Codex | [thread writer lock file](/docs/agents/codex#readiness) |
| Pi | [session reference published by the integration](/docs/agents/pi#readiness) |
| OpenCode | [nonce round trip through the composer](/docs/agents/opencode#readiness) |

each agent page records the signal with its measurements.

## delivery

orchestratr confirms a message by reading the delivery record that the agent writes when it
accepts the message. the method is the same for every kind:

<Steps>
<Step>

take a watermark before submitting: a byte offset or a line count, depending on the file. a
missing file counts as zero.

</Step>
<Step>

submit the text.

</Step>
<Step>

poll from the watermark. discard an incomplete final line.

</Step>
<Step>

accept the first new delivery record that matches the submitted text and belongs to this
agent's session.

</Step>
</Steps>

the measurements forced two rules:

- **compare positions in the file, not timestamps inside records.** one kind writes a delivery
  record whose internal timestamp is earlier than the moment the record can be read.
- **match every shape a delivery can take.** a message sent mid turn can be recorded in a
  different shape from one sent at rest. on one kind, a mid turn message never produces the
  record type that a naive check looks for, so a check that matches only that type reports
  failure for every message sent mid turn.

a kind can also write the message to more than one file, with very different timing. one kind
records it in under half a second in one file, and not until the running tool returns in
another, measured at 17.82 seconds and unbounded. the file to poll is named on each
[agent page](/docs/agents), and the choice is not interchangeable.

| kind | delivery record |
|---|---|
| Claude Code | [transcript](/docs/agents/claude#delivery) |
| Codex | [history file](/docs/agents/codex#delivery) |
| Pi | [transcript](/docs/agents/pi#delivery) |
| OpenCode | [SQLite database](/docs/agents/opencode#delivery) |

how the outcome is reported to a caller is defined in
[confirmation](/docs/cli#confirmation).

## state

the backend reports the state. that is the default for every kind.

herdr maintains per-kind detection rules, updates them as the agents change, and already
answers this question. orchestratr keeps no rules of its own and does not read the terminal to
second-guess the answer.

the backend's answer is good enough here because it is not load bearing. correctness rests on
delivery confirmation, which reads the delivery record. state is for reporting: it tells a
caller what an agent is doing.

orchestratr adds a per-kind signal in exactly two cases, both recorded on the
[agent pages](/docs/agents):

1. **readiness at start.** the backend reports an agent as ready while a startup screen is on
   screen, and on one kind 25.4 seconds before its interface has drawn itself. starting an
   agent depends on knowing it is genuinely ready, so orchestratr uses the kind's own signal
   for this one question. this is a must, not a preference.
2. **where the backend has no rule at all and the answer matters.** one kind has no idle rule,
   so its idle answer is a default rather than an observation.

everything else falls back to the backend. if the backend is wrong about a state, the fix
belongs in its detection rules, where every tool that uses it benefits, not in orchestratr.

### state sources

`state_source` in the output names where a state came from.

| value | meaning |
|---|---|
| `backend` | the backend reported the state. the normal case. |
| `pushed` | the kind's integration reported the state to the backend directly. |
| `file` | a per-kind signal, used for the two cases above. |
| `fallback` | the backend matched no rule and returned a default. |
| `liveness` | the process ended. |
