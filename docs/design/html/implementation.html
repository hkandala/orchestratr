Implementation#

This document defines the internal structure. It names no agent. Everything specific to one kind lives in docs/design/agents/.

Layers#

orcr command line
      |  socket, newline JSON
orcr server
      |
   core: registry, lifecycle, state, transcripts
      |                        |
 backend driver          kind adapters
      |                        |
    herdr               agent processes and their files

The command line holds no logic beyond parsing arguments, formatting output, and mapping an error code to an exit code. Every decision happens in the server. Adding a command means adding a method, then a thin wrapper.

The registry#

orcr keeps its own registry entry for every agent it started. The registry is the source of truth for which agents exist and what they are. The backend is a cache of that, and orcr reconciles against it.

Run state is the other way round. The backend reports whether an agent is working, idle or blocked, and orcr does not second-guess it. See section "State" in the CLI reference.

~/.local/state/orcr/registry.json

One registry entry per agent: name, kind, working directory, model, effort, backend pane, agent session id, transcript path, creation time, last known state.

Rules:

  • Write by writing a temporary file and renaming it. Never write in place.
  • Resolve a symbolic link before writing any file orcr does not own. See "Writing a person's configuration" below.
  • Reconcile against the backend at startup and on every list. An agent the backend no longer reports is exited.
  • Key state on the agent session id first and the backend pane second.
  • Never store a terminal identifier. It looks like a stable key and it changes on every restart of the backend.

The backend restores its own agents across a restart, relaunching each with its own resume argument. Treat that as a useful optimization, never as a guarantee. It did not restore every kind in testing, and a pane with no bound session is not restored at all.

The kind adapter#

One adapter per kind. The interface is small on purpose. Most members are data.

MemberKindPurpose
launch_argv(model, effort)dataThe argument list, including the permission bypass argument.
prepare(cwd)actionSet every configuration key that stops a startup screen. Fails loudly.
ready(pid, cwd)predicateTrue when the kind's readiness file says the agent accepts input.
state(pid, cwd)functionThe state from the kind's own file, or nothing if it has none.
watermark(session)functionThe position to resume reading the delivery record from.
confirm(session, watermark, text)functionTrue when the delivery record for this text exists.
session_id(pid, cwd)functionThe agent's own session identifier.
transcript_path(session_id, cwd)functionWhere the conversation is written.
parse(line)functionOne transcript line to one normalized message.
interrupt_keys()dataThe key sequence that stops a turn.
catalogue()actionThe model and effort list.

What the interface deliberately excludes#

There is no screen reading member, no per-kind message sending member, and no per-kind interrupt procedure. Only the key sequence differs, and that is data.

There is no classification of why an agent is blocked. orcr passes through whatever text the source provides.

Where a member may be absent#

state and session_id can return nothing for a kind whose files do not carry them. The core falls back to the backend and records state_source accordingly.

Sending a message#

One procedure, every kind.

send(name, text, immediate):
    a = registry.get(name)                  -> not_found
    if not backend.alive(a)                 -> exited
    if a.state == blocked                   -> blocked, send nothing at all
    if immediate and a.state == working:
        interrupt(a)
        wait until state != working         -> timeout
    if not adapter.ready(a)                 -> not_ready
    w = adapter.watermark(a.session)
    backend.clear_composer(a)
    backend.paste(a, text)
    backend.press_enter(a)
    poll until deadline:
        adapter.confirm(a.session, w, text)  -> delivered
        state became idle and still no record -> possibly_delivered, stop early
        nothing yet, and enters_sent < 2      -> backend.press_enter(a)
    -> possibly_delivered

The three outcomes#

The dividing line is proof, and it comes from one flag: write_attempted, set immediately before the socket write. Every backend failure sorts by which side of that flag it occurred on.

Backend outcomeSideReported
The delivery record appearedafterdelivered
agent_blockedbefore, proven: pane unchanged, text never appearsfailed
Invalid key. The backend validates every key before writing any byte.beforefailed
Agent not found, not running, or gonebeforefailed
invalid_request, unsupported_methodbefore, and a defect in orcrfailed
Connect failure, oversized requestbeforefailed
agent_prompt_stalledafterpossibly_delivered
timeoutafterpossibly_delivered
Internal error, connection closed, malformed replyafterpossibly_delivered
Wrote fine, no record inside the deadlineafterpossibly_delivered

Two mechanical rules keep that table decidable.

Declare the mutation class per request. A request known to change nothing can be reported as a proven failure. A request that can change something cannot.

Send one key per request. A batch of keys that fails part way is ambiguous about which key landed, and that ambiguity would push otherwise provable cases into possibly_delivered.

Retry rules follow from the side, not from the code. Anything on the "before" side can be retried once, except a blocked agent, which is a refusal. Nothing on the "after" side can be retried, because a duplicate is possible. Enter alone is exempt, since re-sending it cannot duplicate a message.

The composer is cleared before every send. orcr does not detect that the composer is empty. It makes it empty. One kind restores unsent text into the composer after an interrupt, and without the clear the next message is submitted joined to that text as one message.

Polling interval is 100 to 200 milliseconds. The deadline is per kind, set well above the worst measured latency.

Stopping early on an idle agent with no delivery record matters for one kind. On that kind the delivery record for a mid turn message does not appear until the running tool call returns. There the deadline is the end of the turn rather than a number. orcr waits for the work and reports possibly_delivered the moment the turn ends without the record. The rule is written once and applies to every kind, because it is never wrong for the others.

Starting an agent#

new(kind, cwd, model, effort, name):
    backend.check()                         -> backend_unavailable
    backend.check_integration(kind)         -> integration_missing
    adapter.prepare(cwd)                    -> fails before anything is launched
    ws = backend.workspace_for(cwd)
    tab = backend.create_tab(ws)
    backend.start(tab, adapter.launch_argv(model, effort))
    poll adapter.ready() until deadline     -> on failure, stop and remove the tab
    registry.put(...)

prepare runs before anything is launched, so a configuration failure costs nothing. A failure after launch removes the tab. orcr never leaves a half started agent.

The backend's own readiness answer is not used. See limitations.md for the evidence. It returned true while a startup screen was displayed on three kinds, and on one kind it returned true 25.4 seconds before the terminal had drawn itself.

Writing a person's configuration#

prepare writes nothing for three of the four kinds. For Claude it writes three keys to the person's configuration file. Three rules.

Resolve the link before writing. A configuration path is often a symbolic link into a repository that the person manages. Writing a temporary file and renaming it over that path replaces the link with a plain file. Every later edit in the repository then silently stops taking effect. Resolve the real path first, then write a temporary file beside the real file and rename it there.

Write only when the key is absent. Never overwrite a value the person set.

Preserve everything else. For a structured format, parse, add the one key, and serialize. For a format that allows the same table twice, check for a duplicate before adding, because appending a second table changes which value wins.

Report what was done: written, already present, or skipped. orcr doctor shows it.

Placement#

One backend session, named orcr. One workspace per distinct working directory. One tab per agent, and the agent runs in that tab's pane. orcr records the pane identifier, because that is what the backend's own methods take.

orcr creates and manages only that session. It never stops or deletes a session it did not create.

Transcripts#

Every kind writes a different format. parse converts one line into the normalized message defined in the CLI reference: sequence, role, time, text, tool names.

Two rules:

  • Never derive a working directory from a transcript path. Every kind mangles the directory into the path, and the mangling is lossy.
  • Tolerate a known path with no file. Some kinds report a transcript path before the file exists.

Following a transcript is a file watch with a poll fallback. Reading must handle a partial final line, because a reader can see a line mid write.

Backend interaction#

orcr speaks the backend's socket directly. It shells out for exactly two things: creating the backend session, which has no socket method, and attaching a terminal, which cannot be an API call.

Handshake on every connection. Compare the protocol number and refuse with one clear error rather than failing method by method.

The backend takes its timeouts in milliseconds. orcr accepts a human duration and converts. This has already cost one round of false failures.

orcr scrubs known child session markers from the environment it gives the herdr server. See agents/claude.md for the marker that disables transcript writing.

Errors#

Nine codes, closed, defined in the CLI reference. Each maps to one exit code.

Specifics go in details, not in new codes. A small code set stays usable only if it is not allowed to grow.

Every message states what orcr looked for. A failure to confirm delivery reports the text and the timeout, so a caller can look for themselves.

Concurrency#

The server handles requests concurrently. Per agent, serialize anything that types: sending, interrupting, and clearing. Two concurrent sends to one agent would interleave keystrokes.

Reads, listing and transcript following need no lock.

Testing#

Three levels:

  1. Adapter unit tests over captured files. Every measurement in docs/design/agents/ came from a captured file, and those files are the fixtures.
  2. Backend tests against a throwaway backend session. Never against a session orcr did not create.
  3. A live test per kind that starts an agent, sends one message, confirms delivery, and stops it.

The second and third levels must run in an isolated configuration directory, and must never write to a person's real configuration file.

For the first level, bb is useful prior art. It records the traffic of each agent as newline delimited JSON, keeps a manifest that pins the agent version beside each recording, and replays the recording in its tests. See packages/provider-bridge-protocol/recordings/ in https://github.com/get-bb/bb.
