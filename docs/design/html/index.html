Purpose#

What orcr is#

orcr runs and controls AI coding agents. It supports four kinds:

  • Claude Code
  • Codex
  • Pi
  • OpenCode

Each agent runs as an interactive terminal program inside a pane that herdr manages. orcr gives every agent an identity, tracks its state, and offers one set of commands that works the same way for all four kinds.

The socket API is the product. The command line tool is one caller of that API. Any program that can open a UNIX socket and write a line of JSON can do everything the command line tool can do.

The problem#

A coding agent runs alone. One terminal, one agent, one person watching it.

Real work needs more than one agent.

  • a reviewer per concern
  • a worker under a verifier
  • a nightly job that triages issues

That work often needs agents of different kinds, because each kind has different strengths and its own subscription quota.

Why interactive sessions#

Each kind can also run without a terminal. orcr does not use that mode. Interactive sessions keep three properties that matter at this scale.

  1. Price. An interactive session bills against a flat subscription plan. A non-interactive call bills for each token. Across many agents this difference sets the total cost.
  2. Control. A person can watch an interactive session while it works, correct it mid turn, and take the terminal over when it goes wrong.
  3. One interface. Each kind has a different non-interactive mode, with different flags and different output. The interactive terminal is the one surface all four kinds share.

What orcr provides#

  • Identity. Every agent gets a stable name and id that survive a restart.
  • Placement. Agents that share a working directory share a workspace.
  • Lifecycle. Start an agent, send it a message, interrupt it, attach to it, stop it.
  • State. One state vocabulary for all four kinds.
  • Transcripts. Read the conversation of any agent in one format.
  • Catalogue. List the models and effort values each kind accepts.

Scope#

orcr controls the agents it starts. It does not adopt agents that another tool started.

orcr starts every agent with permission prompts turned off. An agent that orcr starts can run any command in its working directory without asking. This is deliberate. orcr offers no command to approve or reject a single action.

herdr is the terminal backend. orcr requires herdr, and requires the herdr integration for each kind it drives.

Design rules#

These rules decide arguments. Read them before proposing a change.

  1. One behavior for all kinds. Where the agents differ, orcr hides the difference or states it. orcr does not grow a separate code path for each kind.
  2. Per-kind knowledge is data, not code. Launch arguments and startup steps live in a table.
  3. Do not reimplement herdr. If herdr answers a question, orcr asks herdr.
  4. Fail closed. When orcr cannot confirm that an action is safe, it refuses and says why.
  5. The socket API comes first. A command line feature that the API cannot express is a bug in the API.
  6. Say what is not known. An honest gap is more useful than a confident guess.

CLI reference and socket API#

This document defines the complete orcr contract. Part 1 defines the command line tool. Part 2 defines the socket API. The command line tool is a caller of the socket API. Every command maps to one API method.

Part 1 — Command line#

1.1 Conventions#

Names#

Every agent has one identifier, its name. orcr generates a name when you do not supply one. A generated name is the kind, a hyphen, and the lowest free number for that kind.

claude-1  codex-1  codex-2  pi-1  opencode-1

A name is unique across orcr. Every command that acts on an agent takes a name.

Output#

Text output is the default. It is for a person to read. Its exact layout can change between releases.

--json output is stable. Programs must use --json. Each command documents its JSON shape below. All JSON output is a single object, never a bare array.

Times in JSON are RFC 3339 strings in UTC. Time arguments accept an RFC 3339 string, a Unix timestamp in seconds, or a relative duration such as 30m or 2h.

Durations accept a unit suffix of s, m, or h. A bare number means seconds.

Exit codes#

CodeMeaningError code
0Successnone
1Internal failureinternal
2The command was used wronglyinvalid_request
3The agent does not existnot_found
4The agent cannot accept this action nownot_ready, blocked
5The action did not finish in timetimeout
6herdr is missing, stopped, or a different protocolbackend_unavailable
7The herdr integration for this kind is missing or staleintegration_missing

The set is closed. Every failure maps to one of these seven codes.

State#

An agent is always in exactly one state.

StateMeaning
workingThe agent is running a turn.
blockedThe agent waits for a person to answer something on screen.
idleThe agent is ready for a message.
exitedThe agent process ended.
unknownorcr cannot determine the state.

orcr evaluates liveness first. A dead process is exited even when the last known screen said working.

1.2 orcr agent new#

Start a new agent.

orcr agent new --kind <kind> [--model <model>] [--effort <effort>]
               [--cwd <dir>] [--name <name>] [--prompt <text>]
               [--timeout <duration>] [--json]
FlagDefaultMeaning
--kindrequiredclaude, codex, pi, or opencode.
--modelthe kind's own defaultThe value reaches the agent unchanged.
--effortthe kind's own defaultThe value reaches the agent unchanged.
--cwdthe current directoryThe working directory of the agent.
--namegeneratedThe name of the agent. Must be unique.
--promptnoneA first message, sent once the agent is ready.
--timeout120sHow long to wait for the agent to become ready.

What it does#

  1. Make sure herdr is running and speaks a supported protocol. Make sure the herdr integration for this kind is installed and current.
  2. Find or create the workspace for --cwd. Agents that share a working directory share a workspace.
  3. Create a tab. Start the agent in the tab's pane, with permission prompts turned off.
  4. Run the startup steps for the kind. A kind can open a startup screen that permission bypass does not remove. The startup steps clear those screens.
  5. Wait until the agent reports a ready state that orcr can confirm. See section 1.11.
  6. Record the agent in the orcr registry.
  7. If --prompt was given, send it as a message.

orcr agent new fails if the agent does not reach a confirmed ready state inside --timeout. It does not leave a half started agent behind. It stops the agent and removes the tab.

--model and --effort are not validated against a catalogue. orcr passes them through. Run orcr models to see what a kind accepts.

Output#

{
  "name": "codex-1",
  "kind": "codex",
  "cwd": "/Users/me/code/project",
  "model": "gpt-5.6-sol",
  "effort": "high",
  "state": "idle",
  "created_at": "2026-09-18T09:14:02Z"
}

1.3 orcr agent list#

List the agents that orcr started.

orcr agent list [--kind <kind>] [--state <state>] [--cwd <glob>]
                [--since <time>] [--json]
FlagMeaning
--kindShow only this kind.
--stateShow only agents in this state.
--cwdShow only agents whose working directory matches this glob.
--sinceShow only agents created at or after this time.

orcr reconciles its registry against herdr on every call. An agent that herdr no longer reports is exited.

{
  "agents": [
    {
      "name": "codex-1",
      "kind": "codex",
      "cwd": "/Users/me/code/project",
      "model": "gpt-5.6-sol",
      "effort": "high",
      "state": "working",
      "state_source": "rule:osc_title_working",
      "created_at": "2026-09-18T09:14:02Z",

1.4 orcr agent status#

Show one agent, and optionally wait for it to change.

orcr agent status <name> [--wait <state>] [--timeout <duration>] [--json]
FlagDefaultMeaning
--waitnoneReturn when the agent reaches this state.
--timeout300sGive up after this long. Exit code 5.

--wait accepts one state or several, separated by commas. --wait idle,blocked returns on whichever comes first.

Without --wait the command returns at once. Output is one agent object, as in orcr agent list.

1.5 orcr agent read#

Read the conversation of an agent.

orcr agent read <name> [--last <n>] [--format text|jsonl] [--follow] [--json]
FlagDefaultMeaning
--last50Show the last N messages. --last 0 shows all.
--formattexttext for people, jsonl for programs.
--followoffKeep the output open and print new messages as they arrive.

orcr reads the transcript that the agent itself writes. It does not read the terminal. Every kind stores its transcript differently. orcr converts all of them into one shape.

text renders one block per message: the role, the time, and the content. Tool calls render as a one line summary, not as full arguments and results.

jsonl prints one JSON object per line.

{"seq":12,"role":"assistant","at":"2026-09-18T09:20:31Z","text":"...","tools":["Bash","Read"]}
FieldMeaning
seqPosition in the conversation, starting at 1.
roleuser, assistant, or system.
atWhen the message was recorded.
textThe message text.
toolsNames of the tools this message called. Empty when there are none.

A transcript can be absent even when the agent runs. Some kinds do not write a file until the first turn finishes. orcr agent read reports an empty conversation in that case. It does not fail.

1.6 orcr agent message#

Send a message to an agent.

orcr agent message <name> <text> [--immediate] [--timeout <duration>] [--json]
FlagDefaultMeaning
--immediateoffInterrupt the current turn first.
--timeoutthe kind's own deadlineHow long to wait for delivery confirmation.

Read the text from standard input by passing - as the text.

What it does#

  1. Read the state. Refuse when the agent is blocked, exited, or unknown. See section 1.11.
  2. With --immediate, interrupt the agent and wait for it to become idle. This is the same as running orcr agent interrupt and then orcr agent message.
  3. Clear the composer.
  4. Paste the text.
  5. Press Enter.
  6. Confirm that the message was delivered.

Steps 1 to 6 are the same for every kind.

A message sent while the agent is working reaches the model at the next tool call the agent makes. If the turn makes no further tool call, the message runs as the next turn. This is the behavior of all four kinds. Each kind uses a different word for it on screen.

A blocked agent#

When the agent is blocked, orcr refuses before it sends anything. It does not clear the dialog, and it does not type past it.

orcr: agent codex-1 is blocked and is waiting for a person.
      orcr cannot answer it. Attach and clear it first:
        orcr agent attach codex-1

Exit code 4, error code blocked.

This is the one case where orcr knows the message was never sent, because the backend proved it: a send to a blocked agent leaves the pane unchanged and the text never appears.

Confirmation#

There are three outcomes.

OutcomeMeaningExit
deliveredorcr read the agent's own record of this message.0
possibly_deliveredorcr wrote the keystrokes and saw no record inside the timeout.5
failedNothing was sent, and orcr can prove it.4

orcr confirms delivery by reading the delivery record that the agent itself writes when it accepts a message. It does not read the terminal, and it does not treat a keystroke as proof. Section 1.11 defines the record for each kind, and every kind has one. On three kinds it is a file written for this purpose. On Pi it is the transcript, which costs a longer wait mid turn.

failed means nothing happened. The agent was blocked, or the agent is gone, or the backend refused the request before writing any bytes. The dividing line is proof: orcr reports failed only when it knows nothing reached the terminal. Retrying is safe.

possibly_delivered means orcr does not know. The keystrokes went out, Enter was re-sent, and the delivery record never appeared. The message can still arrive. Retrying is not safe, because a duplicate is possible. Look at the agent before doing anything.

The middle value exists because from outside the agent there is no way to separate "written with no effect" from "written and working slowly". Both of the known silent-drop modes return success from the backend. Naming that state honestly is better than sorting it into either neighbor.

orcr: message to codex-1 could not be confirmed after 5s.
      The keystrokes were sent. The agent may still act on them.
      Do not resend without checking:
        orcr agent read codex-1 --last 5

Retrying#

orcr never re-sends the text. A second copy of the text is a duplicate message whenever the first one landed late.

orcr does re-send the Enter key. Pressing Enter again cannot duplicate a message.

  • If the text is sitting unsubmitted in the composer, Enter submits it.
  • If the composer is empty, Enter does nothing.

This recovers the case where the paste arrived and the submission did not, which is otherwise reported as a plain failure.

Enter is re-sent at most twice, only while delivery is still unconfirmed, and never after the agent has been seen to leave idle.

{
  "name": "codex-1",
  "state_before": "working",
  "result": "delivered",
  "confirmed_at": "2026-09-18T09:22:10Z",
  "latency_ms": 496
}

possibly_delivered returns the same object with result set and no confirmed_at, plus the timeout that elapsed. It is an error response, with code timeout, because a caller that ignores the distinction must not read it as success.

failed returns an error with the code that proves it: blocked, not_found, exited, or invalid_request.

1.7 orcr agent interrupt#

Stop the current turn. Do not send anything.

orcr agent interrupt <name> [--timeout <duration>] [--json]

--timeout defaults to 10s.

orcr sends the interrupt for the kind and waits for the agent to leave working. If the agent is still working after 3 seconds, orcr sends the interrupt once more and waits again. orcr never sends it a third time.

The interrupt itself is one key sequence per kind, held as data. Three kinds take one Escape. One kind ignores a single Escape and needs two, with the second inside 5 seconds of the first. On two kinds, two Escapes at rest open a destructive view. See docs/design/agents/.

orcr sends the interrupt only while the agent is working. If the agent is not working, the command succeeds and does nothing. This is what keeps orcr from ever sending the sequence that opens the destructive view.

1.8 orcr agent attach#

Give your terminal to the agent.

orcr agent attach <name> [--takeover]

This replaces your shell with the agent's terminal until you detach. It is the only command that is not available over the socket API, because it hands over a terminal rather than returning data.

--takeover detaches any other client that is attached.

1.9 orcr agent stop#

Stop an agent and remove its tab.

orcr agent stop <name> [--json]

orcr asks the agent to exit, waits, and then closes the pane. The agent's transcript stays on disk. The registry entry stays in the orcr registry with state exited.

1.10 orcr models#

List the models and effort values each kind accepts.

orcr models [--kind <kind>] [--json]

orcr queries each kind directly on every run. There is no cache. orcr probes the four kinds at the same time, so the command takes about as long as the slowest probe, which is about 30 seconds. No probe starts a billed turn.

orcr starts a short lived server process for one kind, and stops it before the command returns. See docs/design/agents/opencode.md.

--model and --effort on orcr agent new are not checked against this list. The list tells you what to pass. It does not gate what you pass.

      "default_model": "gpt-5.6-sol",

          "display_name": "GPT-5.6-Luna",

1.11 Readiness and delivery#

orcr holds no screen patterns and maintains no screen matching code.

The backend derives some of its state by reading the terminal, under per-kind rules that it maintains and updates. Readiness and delivery both come from files the agent writes, because the terminal cannot be trusted for either. See limitations.md for the measured failures.

So orcr answers three questions from the agent's own files.

Remove what can stall, do not answer it#

An agent stops and waits for a person in three ways. orcr removes all three before launch rather than detecting them afterwards.

  1. A startup screen, below.
  2. A tool whose job is to ask the person something. Every kind can be told not to load these. The exact names and syntax are in docs/design/agents/.
  3. A program the agent starts inside a shell command that waits for input of its own:
  4. an interactive rebase
  5. a pager
  6. a host key confirmation
  7. a login dialog

The third is the same for every kind, so orcr sets it once in the environment it gives every agent.

EDITOR=true  VISUAL=true  GIT_EDITOR=true
PAGER=cat    GIT_PAGER=cat
GIT_TERMINAL_PROMPT=0  CI=1

Without this an agent can stall inside a shell command that orcr cannot see. That is worse than a dialog, because no state reports it.

VISUAL is not optional. It takes precedence over EDITOR in most editor selection. Leaving it out was proven to hand a real editor the terminal on one kind despite EDITOR=true. GIT_PAGER is separate from PAGER for the same reason.

Setting these in the environment is not always enough. One kind captures a shell snapshot at startup and applies it after orcr's environment, which silently defeats EDITOR. For that kind orcr also sets them through the agent's own configuration. See docs/design/agents/codex.md.

Remove the startup screens, do not answer them#

Every kind shows at least one screen before it accepts input. Permission bypass removes none of them. Each screen has a configuration key or a launch argument that stops it appearing.

orcr sets those before it launches the agent. A screen that never appears needs no detection and no keystroke.

Three of the four kinds carry every startup setting as a launch argument or as inline configuration, so orcr writes no file for them.

Claude is the exception. Three of its keys have no launch form, so orcr writes them to the person's configuration: the folder trust record, and two keys that clear the theme picker and the security notes screen. orcr writes a key only when it is absent, and writes the trust key only for the working directory. The result is the state that answering the dialogs once produces. See docs/design/agents/claude.md.

The write must follow a symbolic link, so orcr resolves the real path first and writes there.

When orcr cannot set a key, orcr agent new fails before launching. It does not start an agent that will stop on a dialog.

Readiness#

Each kind has a signal that appears only after every startup screen is cleared. orcr waits for that signal. On three kinds it is a file the agent writes. On Pi it is the session reference that the herdr integration publishes.

The test that makes a signal trustworthy is the negative one. A signal is only usable if it stays absent while a dialog is on screen. Several obvious candidates fail that test by more than a minute.

Per-kind signals, with their measurements, are in docs/design/agents/.

Delivery#

orcr confirms a message by reading the delivery record the agent writes when it accepts the message.

The method is the same for every kind:

  1. Take a watermark before submitting. A byte offset or a line count, depending on the file. A missing file counts as zero.
  2. Submit the text.
  3. Poll from the watermark. Discard an incomplete final line.
  4. Accept the first new delivery record that matches the submitted text and belongs to this agent's session.

Two rules that the measurements forced:

  • Compare positions in the file, not timestamps inside records. One kind writes a delivery record whose internal timestamp is earlier than the moment the record can be read.
  • A message sent mid turn can be recorded in a different shape from one sent at rest. On one kind a mid turn message never produces the record type that a naive check looks for. A check that matches only that type reports failure for every message sent mid turn.

A kind can also write the message to more than one file, with very different timing. One kind records it in under half a second in one file, and not until the running tool returns, measured at 17.82 seconds and unbounded, in another. The per-kind file to poll is named in docs/design/agents/, and the choice is not interchangeable.

State#

The backend reports the state. That is the default for every kind.

herdr maintains per-kind detection rules, updates them as the agents change, and already answers this question. orcr does not keep rules of its own and does not read the terminal to second-guess the answer.

The backend's answer is good enough here because it is not load bearing. Correctness rests on delivery confirmation, which reads the delivery record. State is for reporting: it tells a caller what an agent is doing.

orcr adds a per-kind signal in exactly two cases, both recorded in docs/design/agents/.

  1. Readiness at start. The backend reports an agent as ready while a startup screen is on screen, and on one kind 25.4 seconds before its interface has drawn itself. Starting an agent depends on knowing it is genuinely ready, so orcr uses the kind's own signal for this one question. This is a must, not a preference.
  2. Where the backend has no rule at all and the answer matters. One kind has no idle rule, so its idle answer is a default rather than an observation.

Anything else falls back to the backend. If the backend is wrong about a state, the fix belongs in its detection rules, where every tool that uses it benefits, not in orcr.

state_source in the output names where a state came from.

ValueMeaning
backendThe backend reported the state. The normal case.
pushedThe kind's integration reported the state to the backend directly.
fileA per-kind signal, used for the two cases above.
fallbackThe backend matched no rule and returned a default.
livenessThe process ended.

1.12 orcr doctor#

Report whether orcr can work.

orcr doctor [--json]

It checks, and prints one line for each:

  • herdr is installed, running, and speaks a supported protocol.
  • The herdr integration for each kind is installed and current.
  • Each kind's binary is present, and its version.
  • The orcr registry is readable and agrees with herdr.

Exit code 0 when everything passes. Exit code 6 or 7 on the first failure that stops orcr from working.

1.13 orcr serve#

Run the socket API server.

orcr serve [--socket <path>]

The default socket path is $XDG_RUNTIME_DIR/orcr/orcr.sock, and ~/.local/state/orcr/orcr.sock when XDG_RUNTIME_DIR is not set.

Every other orcr command starts this server if it is not already running, and then connects to it. You do not have to run orcr serve yourself.

Part 2 — Socket API#

2.1 Transport#

A UNIX domain stream socket. The framing is newline delimited JSON. One compact JSON object per line, UTF-8 encoded, terminated by \n. There is no length prefix and no header.

A single connection carries many requests and their responses, in any order. A response carries the id of its request. A caller can have several requests in flight at once.

The maximum frame size is 8 MiB. A larger frame closes the connection.

The first frame a caller sends must be hello. The server rejects every other method before hello with invalid_request.

Implementation#

This document defines the internal structure. It names no agent. Everything specific to one kind lives in docs/design/agents/.

Layers#

orcr command line
      |  socket, newline JSON
orcr server
      |
   core: registry, lifecycle, state, transcripts
      |                        |
 backend driver          kind adapters
      |                        |
    herdr               agent processes and their files

The command line holds no logic beyond parsing arguments, formatting output, and mapping an error code to an exit code. Every decision happens in the server. Adding a command means adding a method, then a thin wrapper.

The registry#

orcr keeps its own registry entry for every agent it started. The registry is the source of truth for which agents exist and what they are. The backend is a cache of that, and orcr reconciles against it.

Run state is the other way round. The backend reports whether an agent is working, idle or blocked, and orcr does not second-guess it. See section "State" in the CLI reference.

~/.local/state/orcr/registry.json

One registry entry per agent: name, kind, working directory, model, effort, backend pane, agent session id, transcript path, creation time, last known state.

Rules:

  • Write by writing a temporary file and renaming it. Never write in place.
  • Resolve a symbolic link before writing any file orcr does not own. See "Writing a person's configuration" below.
  • Reconcile against the backend at startup and on every list. An agent the backend no longer reports is exited.
  • Key state on the agent session id first and the backend pane second.
  • Never store a terminal identifier. It looks like a stable key and it changes on every restart of the backend.

The backend restores its own agents across a restart, relaunching each with its own resume argument. Treat that as a useful optimization, never as a guarantee. It did not restore every kind in testing, and a pane with no bound session is not restored at all.

What the interface deliberately excludes#

There is no screen reading member, no per-kind message sending member, and no per-kind interrupt procedure. Only the key sequence differs, and that is data.

There is no classification of why an agent is blocked. orcr passes through whatever text the source provides.

Where a member may be absent#

state and session_id can return nothing for a kind whose files do not carry them. The core falls back to the backend and records state_source accordingly.

Sending a message#

One procedure, every kind.

send(name, text, immediate):
    a = registry.get(name)                  -> not_found
    if not backend.alive(a)                 -> exited
    if a.state == blocked                   -> blocked, send nothing at all
    if immediate and a.state == working:
        interrupt(a)
        wait until state != working         -> timeout
    if not adapter.ready(a)                 -> not_ready
    w = adapter.watermark(a.session)
    backend.clear_composer(a)
    backend.paste(a, text)
    backend.press_enter(a)
    poll until deadline:
        adapter.confirm(a.session, w, text)  -> delivered
        state became idle and still no record -> possibly_delivered, stop early
        nothing yet, and enters_sent < 2      -> backend.press_enter(a)
    -> possibly_delivered

The three outcomes#

The dividing line is proof, and it comes from one flag: write_attempted, set immediately before the socket write. Every backend failure sorts by which side of that flag it occurred on.

Backend outcomeSideReported
The delivery record appearedafterdelivered
agent_blockedbefore, proven: pane unchanged, text never appearsfailed
Invalid key. The backend validates every key before writing any byte.beforefailed
Agent not found, not running, or gonebeforefailed
invalid_request, unsupported_methodbefore, and a defect in orcrfailed
Connect failure, oversized requestbeforefailed
agent_prompt_stalledafterpossibly_delivered
timeoutafterpossibly_delivered
Internal error, connection closed, malformed replyafterpossibly_delivered
Wrote fine, no record inside the deadlineafterpossibly_delivered

Two mechanical rules keep that table decidable.

Declare the mutation class per request. A request known to change nothing can be reported as a proven failure. A request that can change something cannot.

Send one key per request. A batch of keys that fails part way is ambiguous about which key landed, and that ambiguity would push otherwise provable cases into possibly_delivered.

Retry rules follow from the side, not from the code. Anything on the "before" side can be retried once, except a blocked agent, which is a refusal. Nothing on the "after" side can be retried, because a duplicate is possible. Enter alone is exempt, since re-sending it cannot duplicate a message.

The composer is cleared before every send. orcr does not detect that the composer is empty. It makes it empty. One kind restores unsent text into the composer after an interrupt, and without the clear the next message is submitted joined to that text as one message.

Polling interval is 100 to 200 milliseconds. The deadline is per kind, set well above the worst measured latency.

Stopping early on an idle agent with no delivery record matters for one kind. On that kind the delivery record for a mid turn message does not appear until the running tool call returns. There the deadline is the end of the turn rather than a number. orcr waits for the work and reports possibly_delivered the moment the turn ends without the record. The rule is written once and applies to every kind, because it is never wrong for the others.

Starting an agent#

new(kind, cwd, model, effort, name):
    backend.check()                         -> backend_unavailable
    backend.check_integration(kind)         -> integration_missing
    adapter.prepare(cwd)                    -> fails before anything is launched
    ws = backend.workspace_for(cwd)
    tab = backend.create_tab(ws)
    backend.start(tab, adapter.launch_argv(model, effort))
    poll adapter.ready() until deadline     -> on failure, stop and remove the tab
    registry.put(...)

prepare runs before anything is launched, so a configuration failure costs nothing. A failure after launch removes the tab. orcr never leaves a half started agent.

The backend's own readiness answer is not used. See limitations.md for the evidence. It returned true while a startup screen was displayed on three kinds, and on one kind it returned true 25.4 seconds before the terminal had drawn itself.

Writing a person's configuration#

prepare writes nothing for three of the four kinds. For Claude it writes three keys to the person's configuration file. Three rules.

Resolve the link before writing. A configuration path is often a symbolic link into a repository that the person manages. Writing a temporary file and renaming it over that path replaces the link with a plain file. Every later edit in the repository then silently stops taking effect. Resolve the real path first, then write a temporary file beside the real file and rename it there.

Write only when the key is absent. Never overwrite a value the person set.

Preserve everything else. For a structured format, parse, add the one key, and serialize. For a format that allows the same table twice, check for a duplicate before adding, because appending a second table changes which value wins.

Report what was done: written, already present, or skipped. orcr doctor shows it.

Placement#

One backend session, named orcr. One workspace per distinct working directory. One tab per agent, and the agent runs in that tab's pane. orcr records the pane identifier, because that is what the backend's own methods take.

orcr creates and manages only that session. It never stops or deletes a session it did not create.

Transcripts#

Every kind writes a different format. parse converts one line into the normalized message defined in the CLI reference: sequence, role, time, text, tool names.

Two rules:

  • Never derive a working directory from a transcript path. Every kind mangles the directory into the path, and the mangling is lossy.
  • Tolerate a known path with no file. Some kinds report a transcript path before the file exists.

Following a transcript is a file watch with a poll fallback. Reading must handle a partial final line, because a reader can see a line mid write.

Backend interaction#

orcr speaks the backend's socket directly. It shells out for exactly two things: creating the backend session, which has no socket method, and attaching a terminal, which cannot be an API call.

Handshake on every connection. Compare the protocol number and refuse with one clear error rather than failing method by method.

The backend takes its timeouts in milliseconds. orcr accepts a human duration and converts. This has already cost one round of false failures.

orcr scrubs known child session markers from the environment it gives the herdr server. See agents/claude.md for the marker that disables transcript writing.

Errors#

Nine codes, closed, defined in the CLI reference. Each maps to one exit code.

Specifics go in details, not in new codes. A small code set stays usable only if it is not allowed to grow.

Every message states what orcr looked for. A failure to confirm delivery reports the text and the timeout, so a caller can look for themselves.

Concurrency#

The server handles requests concurrently. Per agent, serialize anything that types: sending, interrupting, and clearing. Two concurrent sends to one agent would interleave keystrokes.

Reads, listing and transcript following need no lock.

Testing#

Three levels:

  1. Adapter unit tests over captured files. Every measurement in docs/design/agents/ came from a captured file, and those files are the fixtures.
  2. Backend tests against a throwaway backend session. Never against a session orcr did not create.
  3. A live test per kind that starts an agent, sends one message, confirms delivery, and stops it.

The second and third levels must run in an isolated configuration directory, and must never write to a person's real configuration file.

For the first level, bb is useful prior art. It records the traffic of each agent as newline delimited JSON, keeps a manifest that pins the agent version beside each recording, and replays the recording in its tests. See packages/provider-bridge-protocol/recordings/ in https://github.com/get-bb/bb.

Environment#

orcr reads no environment variable for its own settings.

orcr removes known child session markers from the environment it passes to the herdr server. One of them silently disables transcript writing for a kind, and orcr confirms message delivery by reading transcripts.

Limitations#

Everything here is a known limit of the design, not a defect to be fixed during implementation. Each entry states the limit, the evidence, and the action for a caller.

Scope#

orcr controls only the agents it started. An agent started by a person, or by another tool, is invisible to orcr. orcr agent list shows nothing for it.

Permissions are bypassed on every agent. An agent that orcr starts can run any command in its working directory without asking. There is no command to approve or reject a single action, and no setting that turns this off. Start agents in directories where that is acceptable.

orcr disables the tools that stop and ask a person a question. Bypassing permissions removes the permission prompt, and it does not remove an agent's own question tool. So orcr also turns those tools off at launch, on every kind. orcr also sets an environment that stops a program started inside a shell command from waiting for input. This was verified on all four kinds: the model answers in prose instead, and the turn completes.

That makes blocked uncommon. It does not make it impossible, and orcr still cannot clear it. When an agent is blocked, orcr agent message refuses and tells a person to attach.

These can still stop and wait, and none of them can be switched off:

  • A usage limit or quota dialog. Three kinds have one.
  • An authentication or sign-in flow when a token expires.
  • A dialog raised by an MCP server, including its own consent flows.
  • A model migration or upgrade notice.
  • On one kind, a dialog offered when resuming a large session.

Reporting differs by kind.

  • Claude's status file gives the reason, distinguishing a permission prompt from input needed.
  • OpenCode exposes a pending request on its own port.
  • Codex carries typed waiting states in a protocol orcr does not speak.
  • Pi reports nothing.

herdr is required. orcr does not run without it, and requires the herdr integration for each kind it drives. orcr doctor reports a missing or stale integration.

The backend reports agents as ready when they are not#

Of twelve reachable screens where an agent could not accept input, the backend reported only two of them correctly. It reported the other ten as ready. The list includes startup trust dialogs, command pickers, model selection screens, and a composer still holding unsent text.

The backend's own readiness answer is also early, by 2.6 to 5.1 seconds on one kind and by about 25 seconds on another.

orcr therefore does not use the backend's readiness answer, and confirms every message against the delivery record rather than against the fact that keys were sent.

Per kind#

Claude#

  • The transcript does not exist before the first prompt, although the session start event reports its path earlier. It is created early in the first turn, not when the turn finishes. orcr agent read returns an empty conversation rather than failing.
  • An inherited CLAUDE_CODE_CHILD_SESSION variable disables transcript writing completely, which disables delivery confirmation. orcr removes CLAUDE_CODE_* from the environment it gives the backend. If you start the herdr server yourself from inside a Claude session, scrub it yourself.
  • A brand new configuration directory triggers every startup screen. Pointing kind.claude.home at a fresh directory makes startup harder, not easier.
  • Permission bypass fails when the user id is zero. Claude refuses --dangerously-skip-permissions under root or sudo, and states that reason. Do not run orcr as root.
  • Claude writes the work of each subagent to its own file, beside the main transcript: projects/<mangled cwd>/<session uuid>/subagents/agent-<id>.jsonl, with a .meta.json file next to it. orcr agent read reads the main transcript only, so subagent work does not appear. Each of these files repeats the parent session id inside it, so a reader must key them on the file name. orcr does not read them.

Codex#

  • A message sent mid turn does not reach the rollout transcript until the running tool returns. One measurement was 17.82 seconds and the delay is unbounded. orcr confirms delivery from the history file instead, which records it in under half a second.
  • If a hooks file exists in the Codex home, Codex shows a hook review screen. Hooks load untrusted and never run until trusted. The herdr integration for Codex is a hook, so an untrusted integration silently never reports and the agent never binds its session. orcr doctor reports this state.

Pi#

  • A message sent mid turn is confirmed late. Pi records a message when it acts on it, not when it accepts it, so the delivery record does not appear until the running tool call returns. One measurement was 39.6 seconds behind a 60 second command, and the delay is bounded only by the tool's own runtime. Allow for it in --timeout, or send when the agent is idle. orcr stops waiting the moment the turn ends without the record, and reports possibly_delivered.
  • Pi can never be reported as blocked. It has no blocked screen rules, and the blocked event the herdr integration for Pi listens for is emitted by nothing in Pi. Every blocking Pi dialog reached during testing was reported as idle.
  • Pi is the one kind where a message sent to a waiting agent answers the dialog. The state says idle, so orcr's refusal never fires, the text is typed into the dialog, and Enter selects the highlighted option. Reproduced live: the message is lost, and a choice is made on the person's behalf.
  • Pi ships nothing that waits for a person, so the risk comes from extensions, which orcr leaves alone. Clear such a dialog yourself with orcr agent attach.
  • The complete set of effort values needs one process per model. orcr models reports them only for a named model.

Two of these would be removed by a small Pi extension loaded at launch: late mid turn confirmation, which the extension reduced to 0.47 seconds, and the inability to report blocked. It is not part of orcr, and orcr ships no code that runs inside an agent.

OpenCode#

  • OpenCode must be 1.18.29 or newer. Below that, the herdr integration for OpenCode loads and never reports.
  • The backend never binds a session for this kind, even on a current build. The integration loads, its hooks fire with a real session id, and its calls return success. The backend accepts the report and discards it. orcr finds the session id from the database instead.
  • The backend has no idle rule for this kind, so its idle answer is a default rather than an observation. orcr does not depend on it.
  • A blocked agent is visible only over HTTP, on the port orcr pins at launch. The database does not record it.
  • An interrupt needs two Escapes, with the second inside 5 seconds of the first. A single Escape does nothing. orcr sends both as one burst, which is the safe end of that window.
  • Listing models starts a short lived server. It is the only kind that needs one, and the only source that carries the per model effort variants.

Behavior you should expect#

possibly_delivered is a real outcome and you have to handle it. It means the keystrokes went out and the delivery record never appeared. The message can still arrive, and a retry can duplicate it. Look at the agent before deciding.

orcr never answers a dialog. When an agent is blocked, orcr refuses and tells you to attach. On one kind, the backend's own send method typed into a directory trust dialog and the Enter key selected "Yes, continue".

orcr agent attach is not available over the socket API. It hands over a terminal rather than returning data.

The backend restores agents across its own restart, but not reliably. Treat it as an optimization. orcr keeps its own registry and reconciles against the backend.

Reported upstream#

Three findings belong to herdr and are better fixed there than worked around here.

  1. Session reports from the herdr integration for OpenCode are accepted and discarded.
  2. Ten of twenty two detection manifests have no positive idle rule, including OpenCode.
  3. The Pi manifest has no blocked rule, and Pi emits no blocked event for the one the herdr integration for Pi listens for.

Not verified#

  • OpenCode: whether its event stream and its database agree on ordering under load, and whether an invalid effort segment fails at launch or silently starts the base model.
  • OpenCode: whether the readiness round trip is safe while a person is attached and typing.
  • Claude: whether a status file survives the process being killed rather than exiting.
  • Claude: whether permission bypass fails under root or sudo. The refusal is recorded in another project, which avoids it by not asking for bypass. orcr did not measure it.
  • Codex: whether the lock file survives the process being killed, and whether the model list ever needs more than one page.
  • Pi: whether the published transcript path changes when a session is resumed.
  • All kinds: behavior when two orcr agents run in the same working directory at once.
  • All kinds: what an approval dialog looks like, for the two kinds where one could not be reached during testing.

Verified live: with these disabled, a request that normally opens a question dialog is answered in prose instead, and the turn completes.

The flag is variadic. It must be last, or it swallows anything that follows. orcr never passes a positional prompt, so this is a constraint on argument order rather than a hazard.

The deny list can also be written in settings, and is the same mechanism:

{"permissions": {"deny": ["AskUserQuestion", "ExitPlanMode", "EnterPlanMode", "Workflow"]}}

Do not write permissions.defaultMode: "bypassPermissions" and expect it to replace the launch flag. It is not equivalent. That key is honored only from the highest priority settings source present. A managed or policy settings file that sets defaultMode silently outranks it, and several hosts ignore it outright. Tested on a machine with a managed settings file: the agent did not enter bypass and the footer showed a different mode.

orcr passes the flag. A setting that can be outranked without saying so is not a way to guarantee anything.

askUserQuestionTimeout accepts 60s, 5m, 10m or never, and defaults to never. It bounds the stall rather than removing it, so orcr removes the tool instead.

dialogExpiry and CLAUDE_CODE_USER_DIALOG_TIMEOUT_MS look relevant and are not. Their own description says local prompts with no remote client are unaffected, which is every dialog orcr will ever see.

The three written keys#

Claude is the only kind for which orcr writes to a configuration file.

  projects["<resolved real path of the working directory>"].hasTrustDialogAccepted = true

Message delivery#

Before submitting, note the transcript line count as a watermark. Treat a missing file as zero. After submitting, poll the transcript every 200 milliseconds and accept either record.

CaseRecord
Agent at resttype is user, and the message content holds the submitted text
Agent workingtype is queue-operation, operation is enqueue, content equals the submitted text

A message sent while the agent is working always produces the queue-operation record first. What happens next depends on the turn.

  • If the turn absorbs it, a second queue-operation follows with operation remove and reason absorbed_mid_turn, plus an attachment row of type queued_command.
  • If the turn ends first, the message is then delivered as an ordinary user record.

So a mid turn message can produce both records, and a check matching only user records misses the first case entirely. orcr matches either and accepts the earliest. Anything that counts messages must treat the pair as one message, not two.

Transcript#

$CLAUDE_CONFIG_DIR/projects/<resolved cwd, every / replaced by ->/<session uuid>.jsonl

The root is the configuration directory, not the home directory, so it moves with CLAUDE_CONFIG_DIR. The directory name is the resolved real working directory with every slash replaced by a hyphen, including the leading one: /private/tmp/work becomes -private-tmp-work. The file name is the session uuid, which is the same value the status file reports.

Pi#

--kind pi

Pi is the weakest instrumented of the four kinds. It has no record of an accepted message and no signal that it is waiting for a person. Both limits are stated below and neither is worked around.

Launch#

pi --approve [--model <provider>/<model>] [--thinking <level>]

Pi's effort argument is --thinking. Its values are per model, and one model accepts only the lowest value. orcr models reports the accepted values.

Startup#

Pi shows no trust dialog in an empty new directory.

It shows a dialog only when the working directory, or an ancestor of it, holds one of these:

  • a .pi/settings.json
  • a .pi subdirectory for extensions, skills, prompts or themes
  • a .pi system prompt file
  • an .agents/skills directory

--approve suppresses the dialog. It is a launch argument, so orcr writes no configuration file for this kind.

Read the two flags carefully, because the names invite the wrong choice.

FlagWhat it does
--approveTrust the project's own files for this run
--no-approveIgnore the project's own files for this run

Both remove the dialog, and they are not interchangeable. --no-approve removes it by discarding the project's configuration: its settings, its extensions, its skills and its system prompt are all skipped. That is a silent loss of the setup a person built.

orcr uses --approve, which answers the trust question instead of avoiding it. This matches the rest of orcr: permissions are already bypassed, so trusting the directory a person asked us to run an agent in is the same decision, not a new one.

Interactive tools#

There is nothing to disable, and orcr disables nothing.

Pi's built-in tools are read, bash, edit, write, grep, find, ls, and powershell on Windows. Only read, bash, edit and write are enabled by default. grep, find and ls are off.

Not one of them waits for a person. Pi is the only kind that needs no tool denial, because it ships nothing to deny.

An extension can register a tool under the same name as a built-in and shadow it, and such a tool survives --no-extensions. So the tool list an agent reports is not by itself evidence about Pi.

orcr also leaves Pi's extensions alone. It passes no --no-extensions and no tool exclusion list. Both were considered and dropped:

  • Disabling extensions breaks a person's own setup, and does not even work completely, because bundled extensions stay loaded regardless.
  • Excluding tool names means guessing the tool names in a person's extensions. The exclusion list is exact-match with no patterns, and it silently ignores a name that does not exist. A guessed list protects against nothing.

What can still block a Pi agent#

An extension, and only an extension.

Pi's extension interface lets an extension open a dialog from a lifecycle hook rather than from a tool, and Pi's own documentation offers this as a use case, with a confirm before a destructive command as its example. Reproduced live: an extension that confirms on each shell call opens a dialog, waits forever, and Pi reports idle throughout.

No launch argument prevents this. It is not a tool, so a tool flag cannot reach it, and a bundled extension cannot be unloaded at all.

orcr accepts this rather than working around it. A person running Pi with a confirming extension has to clear the dialog with orcr agent attach.

Two configuration keys have the same effect and orcr does not use them, because a launch argument is reversible and a file is not:

$PI_CODING_AGENT_DIR/settings.json   defaultProjectTrust = "always"
$PI_CODING_AGENT_DIR/trust.json      {"<canonical absolute cwd>": true}

The path in trust.json must be the resolved real path. Any other form of the path is silently ignored. No environment variable controls trust.

Readiness#

the backend's bound agent session for the pane, once it is not empty

The herdr integration for pi publishes this at its session start event. The negative test passes cleanly: the value stayed absent for 45 seconds with a trust dialog on screen, and appeared 1.2 seconds after the dialog was answered. Over that same period the backend's start response, its status and its interactive flag all reported the agent as ready.

The published value is the transcript path itself, not an identifier. Pi is the only kind where orcr knows the transcript location at readiness, before the file exists.

Message delivery#

Pi has no separate record of an accepted message. The transcript is the only source, and it is the one place where orcr must wait rather than poll for a fixed time.

  • A message sent to a working Pi agent is confirmed late. Use a --timeout that allows for the work in progress, or send after the agent is idle.

Model catalogue#

About two seconds, no server, no billed turn.

It is not free of side effects. OpenCode#

--kind opencode

Version requirement#

OpenCode must be 1.18.29 or newer. The herdr integration for opencode exports an entry point that older builds never call, so on an older build the integration loads, reports nothing, and everything it supplies is silently absent.

orcr doctor checks the version and refuses below the floor.

A binary named opencode is not always OpenCode. During this design work the binary with that name was a redirect stub for an older fork, and every conclusion drawn from it was wrong. Set kind.opencode.binary in the configuration to point at a specific build.

Launch#

opencode --yolo -m <provider>/<model> --hostname 127.0.0.1 --port <port>

--yolo, --auto and --dangerously-skip-permissions are three spellings of one boolean, combined into a single value. OpenCode has no setting between asking and not asking, so there is no safer intermediate mode to prefer here.

Effort cannot be set on the command line for an interactive session. A third path segment on -m does not select a variant. It is appended to the model identifier and breaks the run. The --variant flag that does select one exists on the non-interactive run subcommand only, and is absent from the interactive option list.

Effort comes from configuration, passed inline so that nothing the person owns is modified:

OPENCODE_CONFIG_CONTENT={"agent":{"build":{"model":"<provider>/<model>","variant":"<effort>"}}}

This is merged as the last configuration layer, so it overrides the person's own settings for this process and changes no file. Confirmed in source: the loader calls merge for that layer rather than replacing.

build is the name of a mode. OpenCode calls its modes agents, and a mode is not a model. The -m flag never accepts one. orcr uses the word agent for a session it starts, so the two meanings collide in this kind only.

Proven on the wire rather than on screen. With the key set, the outgoing request carries "reasoning": {"effort": "high", "summary": "auto"}. Without it the field is absent. The database and the HTTP API both report the same resolved variant.

Three rules, each of which fails quietly if broken.

variant without model does nothing. The variant applies only to the agent's configured model, so both keys must be present together. With variant alone the API reports the variant while the request goes out with no reasoning field at all. This is the trap: every observable except the wire says it worked.

The model must publish variants. A variant name that the model does not offer resolves to nothing. orcr models reports the set per model.

It is fixed for the life of the process. The value is read at startup, and editing configuration under a running agent changes nothing until restart. Only orcr agent new sets it.

A person using the in-session model picker outranks all of this. That explains an agent whose effort is not what orcr set.

orcr pins an HTTP port. The interactive program serves its own API on that port. orcr uses it for readiness and for detecting a blocked agent. orcr chooses a free port and records it in the registry.

Interactive tools#

Two layers, and orcr uses both.

OPENCODE_CLIENT=orcr
OPENCODE_PERMISSION={"question":"deny","plan_enter":"deny","plan_exit":"deny"}

The first keeps question out of the registered tool list. The gate is on the client name: any value outside app, cli and desktop works, and orcr is one such value. Do not set OPENCODE_ENABLE_QUESTION_TOOL, which overrides the gate and puts the tool back.

plan_exit is a real tool id but is registered only when an experimental plan mode is enabled and the client is cli. Under orcr's client name it is absent already. plan_enter is not a tool at all, only a permission name, so denying it is harmless and removes nothing.

The second denies them even if registration changes. The variable is merged after the configuration file, so it wins.

The configuration form works too, and has one trap that silently undoes the whole thing:

{"permission": {"*": "allow", "question": "deny",
                "plan_enter": "deny", "plan_exit": "deny"}}

Rules are a flat list resolved by last match. "*": "allow" must come first. Put it last and it re-enables everything that precedes it. Keys accept wildcards, so "quest*": "deny" works.

The older {"tools": {"question": false}} form also works, and loses to any later permission block.

There is no command line flag for this on any subcommand.

Startup#

OpenCode shows no startup screen when at least one model provider resolves. A provider resolves from the generated configuration, from stored credentials, or from a recognized API key variable.

With no provider at all it opens a "Connect a provider" dialog at startup regardless of how fresh the configuration is. orcr asserts a provider in the configuration it generates, and treats that dialog as a launch failure rather than something to answer.

Given a provider, there is nothing to suppress and nothing to answer.

The full screen notice reported on a fork is fork behavior, not OpenCode behavior.

Readiness#

Send a nonce through the agent's own composer and wait for it to come back.

POST /tui/append-prompt   with a nonce
POST /tui/clear-prompt

Repeat until the nonce appears in $XDG_STATE_HOME/opencode/prompt-history.jsonl.

Three details make this work, and getting any of them wrong breaks it silently.

The nonce must be at least 20 characters. That file is appended when the composer is submitted, and when it is cleared while holding a draft of 20 or more trimmed characters. orcr never submits, so the clear is what records the nonce, and a short nonce records nothing.

The return values prove nothing. Both endpoints publish an internal event and return true immediately, before the interface has processed anything. Waiting for the nonce to come back out is the proof, not the response.

These endpoints reach the interface even when a dialog is open, and clear-prompt closes that dialog. So the readiness check must run before orcr considers the agent usable and never as a health check on a live agent, or it can dismiss something a person was answering.

For the same reasons orcr does not use these endpoints to deliver a message.

This round trip is the only signal that is not optimistic. Everything cheaper fires early:

SignalHow early
The backend's own readiness answer25.4 seconds
Log file appears15 seconds
Database file appears, port opens11 seconds
Lock directory appears10 seconds
/tui/* returns HTTP 200still starting

The HTTP server answers before the terminal interface can accept input, so a bare health check is not readiness. Only the round trip through the composer proves the interface is live.

The terminal title becomes correct about 0.63 seconds early and is a usable cheap fallback, but orcr uses the round trip, because the port is already pinned for the blocked check and the round trip costs one more request.

Message delivery#

The delivery record is in the SQLite database.

$XDG_DATA_HOME/opencode/opencode.db          release build
$XDG_DATA_HOME/opencode/opencode-local.db    development build

The file name carries the release channel. Set OPENCODE_DB at launch to pin it, so orcr polls the file the agent writes.

Take the watermark as the current time in milliseconds. After submitting, poll every 200 milliseconds, joining part to message:

part.time_created >= <watermark>
  and message.data ->> '$.role' = 'user'
  and part.data   ->> '$.type' = 'text'
  and part.data   ->> '$.text' matches the submitted text

Reading the database safely#

The database uses write ahead logging. Open it read only with mode=ro. Never open it with immutable=1: that tells SQLite to ignore the write ahead log, and recent writes live there. One observed run had a 757 kilobyte main file and a 609 kilobyte log.

Do not poll the session_input table. It is always empty.

Session identity#

The backend never binds a session for this kind, so orcr finds it itself.

Take part.session_id from the row that confirms the first delivery. No session row exists before the first submission.

The fallback is session.directory, matched against the resolved real path of the working directory. On macOS that is the /private form.

Blocked is available over HTTP only. The permission table stays empty both while a request is pending and after it is answered, and the event table carries only message and session events.

The backend has no idle rule for this kind, so its idle answer is a default rather than an observation. orcr does not depend on it. Readiness comes from the round trip and delivery comes from the database, and neither consults the backend's idle answer.

Interrupt#

Two Escapes, with the second within 5 seconds of the first.

One Escape is ignored. A counter resets after 5 seconds, so two Escapes further apart than that do nothing: 2 seconds apart interrupted in 0.45 seconds, 6 seconds apart did nothing. orcr sends them as one burst, which is the safe end of that window rather than a requirement.

The Escape is dropped entirely when the agent is idle, when a permission or auto overlay is visible, or when the composer does not have focus.

An Escape at rest does nothing here, but Escape is also the dismiss key for the command palette, the model picker and the permission dialog, so orcr sends it only while the agent is working.

  join message m on m.id = p.message_id
 where p.session_id = <session id>
 order by p.time_created, p.id

Order by time_created and then by id. Time alone is not enough. In one database 1122 of 6654 parts shared a millisecond with another part of the same session, and one millisecond held 18 parts.

The tie-break works because parts written in the same millisecond share an id prefix and end in a counter that increases in write order.

Never order by id alone. The prefix is not ordered across sessions. In the same database no row held the same position under id order and under time order.

part.data carries the type: text, reasoning, tool, step-start, step-finish and file. Only message carries the role.

Model catalogue#

Start opencode serve on a free port, read GET /config/providers, and stop the process.

This is the only kind whose catalogue needs a server, and the only source that carries the per model variants where effort lives. orcr stops the server before the command returns.

opencode models --verbose also lists variants and needs no server, but it has no structured output mode. Its lines interleave with pretty printed blocks that a reader must brace match, and it omits the provider metadata and the default model map.

Variants are not in the model cache on disk. The cache format has no variant field. They are produced at runtime.

Steering#

A message sent while the agent is working reaches the model at the next tool call. If the turn makes no further tool call, it runs as a separate turn afterwards, 53 milliseconds after the first one ends. OpenCode's screen calls this a queued message.

Not verified#

  • Whether the HTTP event stream and the database agree on ordering under load.
  • Whether the round trip readiness check is safe when a person is attached and typing.

Why these are separate#

The first version answers one question: can orcr start agents of four kinds, drive them the same way, and report what happened. Everything in this folder widens that question before it has been answered once.

Permissions#

orcr starts every agent with permissions fully bypassed. This file records what replaces permission bypass, and why orcr cannot do it yet.

The intended default: each kind's own auto mode#

Every kind offers a middle setting between asking about each action and checking nothing.

KindFull bypassAuto modeDoes the auto mode ever ask?
Claude--dangerously-skip-permissions--permission-mode autoYes, measured
Codex--yolo--approve-for-meProbably, not provoked
OpenCode--yolo--autoNo such mode exists
Pipermissive by defaultnoneNo such mode exists

The auto modes are better where they exist. They keep each agent's own safety checks on risky actions. On at least one kind, the bypass flag also turns off a sandbox that the auto mode keeps. Bypass is more permissive, and it removes a containment boundary as well.

The bypass flags are documented by their own projects as appropriate for machines that are sandboxed by something else. orcr does not sandbox anything.

So the auto mode is the right default for the kinds that have one, once orcr can answer a dialog. Two of the four have one.

What the measurements showed#

Claude's auto mode asks, and only after a while. All nine graded requests passed silently, including writing to an absolute path outside the workspace, which the classifier reviewed and allowed. The escalation is not per action: after three consecutive classifier denials in one session, a blocking dialog appears reading "Auto mode classifier requires confirmation for this command", and it does not time out. It was still blocking after 172 seconds. There is a second limit at twenty denials in a session, and a third path when the classifier's own transcript outgrows its context window.

A short test says the mode never asks. A long-running agent, which is what orcr is for, eventually hits a counter and stops.

Claude's dontAsk is not the answer. It reads as a mode that never prompts, and it is defined in the shipped bundle as "Don't prompt for permissions, deny if not pre-approved". It does not ask. It refuses. An agent whose tool calls are silently denied fails at its work rather than stalling.

OpenCode has no intermediate mode. --auto, --yolo and --dangerously-skip-permissions are three spellings of one boolean, combined into a single value. There is nothing between asking and not asking.

Pi has no intermediate mode either. It is permissive and offers no gradation.

So this work applies to Claude and Codex. For the other two there is nothing to switch to.

Why orcr cannot use them yet#

An auto mode approves routine actions and stops to ask about risky ones. Stopping to ask is the problem.

orcr has no command to approve or reject anything. An agent that stops to ask sits in its pane until a person opens that pane by hand and answers. Nothing in orcr can clear it, and on one kind nothing in orcr can even report that it happened.

That is the cost of auto mode without an approve command: a per-agent screen reader, which is the one thing orcr has decided not to own.

What has to be built first#

In this order.

  1. Report a waiting agent accurately. A caller must be able to see that an agent stopped to ask, and what it asked. Until then an auto mode turns a working agent into a silent stall.
  2. Answer from orcr. A command that approves or rejects the pending request, and a socket method behind it. Without this, reporting only tells a person to do it by hand.
  3. Then switch the default, per kind, to the auto mode.

Step 1 is the hard one, and it is not uniform. One kind reports a waiting state in a file it already writes. One exposes a pending request over a local HTTP endpoint. One carries typed waiting states in a protocol orcr does not currently speak. One reports nothing at all.

Pi#

If Pi has no graduated mode, it keeps its current behavior after this work lands. orcr should say so rather than implying that a single permissions setting covers all four kinds equally.

What not to do#

Do not add an approve command that works by sending keystrokes to a screen orcr has matched against a pattern. That is the screen reading this design exists to avoid, and it fails in the worst possible direction: pressing the wrong row answers a question that a person was about to answer differently.

An approve command should use the same class of signal the rest of orcr uses. Where a kind offers no such signal, orcr should refuse to answer for that kind and say why.

Delivering a message without typing#

orcr pastes text into the composer and presses Enter, then confirms delivery by reading the delivery record. Two of the four kinds can instead be handed a message directly. That call replaces the keystrokes and the inference, and it returns the outcome.

What is possible today#

KindMechanismNeeds orcr code inside the agent
OpenCodePOST /session/{id}/message on the port orcr already pins at launchNo
PiAn extension calling the agent's own send function, loaded with -eYes
Codexcodex queue, only when a daemon holds the threadNo, but conditional
ClaudeNone usable—

OpenCode#

The cleanest case. orcr already pins an HTTP port at launch for readiness and for the blocked check, so the send becomes one more request on a connection that exists.

The session identifier must be resolved from the agent's own session-selected event, never guessed.

That request also accepts a variant, which is the only way to change effort part way through a session without a person pressing keys. Verified: it took effect in an environment where the configuration route had deliberately been left inert, so the effect came only from the request.

Do not use /tui/append-prompt and /tui/submit-prompt for delivery. They return success unconditionally and do nothing when the composer is not focused, so they offer the ergonomics of an interface with all the uncertainty of a keystroke. They are usable for the readiness round trip only because that check waits for the text to come back out again.

Pi#

Pi exposes a send function to extensions, including a choice of delivering as a steer or as a follow-up. That send function can fix Pi's worst property: today a message sent mid turn is not confirmed until the running tool call finishes, which is unbounded.

It requires shipping an extension, which orcr does not do. See permissions.md for the general shape of that decision. If orcr ever ships one, this is the strongest reason.

Codex#

codex queue reaches a thread that a running app server daemon has loaded. orcr does not run that daemon and does not speak that protocol, so this is only an opportunistic fast path, taken when the daemon happens to exist and to hold the thread. It is not a foundation to build on.

Claude#

There is a cross-session inbox over a local socket that does reach the running interactive session. It is key authenticated, undocumented, versioned, and has no command line client. Revisit only if a supported command appears.

Why the first version types instead#

Typing works on all four kinds and is one code path. Every kind already confirms delivery from its own delivery record, three of them in under half a second, so the uncertainty an interface can remove is already small.

Adopting interface delivery for two kinds means two send implementations behind one interface, for a gain that matters most on the kind where it is hardest to get.

What it would buy#

  • No composer clearing, no bracketed paste, no Enter key, and no Enter retry.
  • No risk of typed text being consumed by a dialog and answering it.
  • possibly_delivered becomes rare or impossible for those kinds, because the call returns a result rather than leaving orcr to infer one.
  • For Pi specifically, the unbounded mid turn confirmation wait disappears.

What it would cost#

  • Two send paths to maintain and test instead of one.
  • A second control plane per kind, versioned separately from the terminal.
  • A new failure mode: a message that reaches a different session from the one shown in the pane. Any implementation must prove it targets the session the person can see, and must fail rather than create a parallel session.

The evidence#

A project solving the same problem across 13 agents delivers every interactive message as a paste plus a separate Enter. It never attempted interface delivery.

That is not proof it is wrong. It is a reason to treat interface delivery as an improvement to prove, rather than the obvious thing everyone does.

Smaller items cut from the first version#

Each item here was considered and left out.

Per-kind interrupt-and-send shortcuts#

Two kinds offer a single key that interrupts the current turn and submits a pending message at the same time. Both were verified to work. Both are better than the general sequence: one key instead of four steps, no polling, and on one of them the risky second Escape becomes structurally impossible because the pending message consumes it.

Cut because the general sequence reaches the same end state on every kind. Two extra code paths to save about two seconds, on a command a person types, is not a trade worth making before the general path has been used in real work.

Shipping our own hooks, plugins or extensions#

orcr installs no code that runs inside an agent. This was reconsidered against a project that ships such integrations, and the evidence closed it.

What their integrations report is a closed list of 19 fields covering session start and end, turn start and stop, and one tool event. None of them reports a pending approval or a pending question. Approvals and questions are read off the screen, despite every one of those hooks being installed.

So the value is one thing: binding a pane to the agent's own session identifier without guessing. The backend already supplies that for three of our four kinds. Where it fails for the fourth, the cause is a backend defect that an orcr hook cannot fix, because the integration already loads and reports correctly and the report is discarded.

Three further reasons not to:

  • A hook on a tool-use event is dangerous as an approval channel. On one agent an empty response reads as a denial, and on another that event fails closed. An orcr hook that crashes stops a person's agent running anything.
  • Installing a hook means editing configuration that the person and other tools also write. The project studied here needs four separate strategies to avoid clobbering, and records a scar where a stale block silently won.
  • Where the backend already installs its own integration on the same event, an orcr hook is the second one on it.

One pattern applies if the situation changes: where an agent has a plugin API and writes no transcript, the right shape is a plugin that writes the transcript, which orcr then tails. None of the four kinds is in that position.

Classifying why an agent is blocked#

An earlier design classified the reason an agent was blocked, so that a caller can tell a permission prompt from a plan review from a trust dialog.

Cut because the backend reports that an agent is blocked but gives no structured reason. Producing one means screen reading, interpreted per kind, which is the most fragile thing orcr can own. orcr reports that an agent is blocked and passes through whatever text the backend already provides.

An abstract effort vocabulary#

A shared set of effort values, such as low, medium and high, mapped onto each kind's own words.

Cut because the words do not line up. Of seven effort words across the four kinds, four appear on only one or two kinds, and two kinds spell the same idea differently. Any mapping has to guess, and a wrong guess changes what a turn costs. --effort passes through as written, and orcr models shows what each kind accepts.

Catalogue caching#

A cache file, invalidated on the agent binary version with a time backstop and a short negative cache for failed probes.

Cut because the probes run in parallel and finish in about thirty seconds, on a command a person runs deliberately. The cache costs an invalidation policy, a staleness question and a partial-answer flag.

A separate identifier for each agent#

A generated id alongside the human readable name.

Cut because the backend already requires names to be unique within a session, and orcr uses one session. A second identifier adds a translation table and nothing else.

Message queueing in orcr#

Holding a message in orcr while an agent is busy, and submitting it when the agent frees up.

Cut because every kind already queues natively and delivers at the next tool call. Building a second queue on top of a working one adds a place for messages to be lost, and makes it unclear which queue a caller is talking to.

Headless mode#

What it means#

A headless agent runs without a terminal. The controlling program speaks a protocol to the agent process directly, and reads structured events instead of screen text.

Every one of the four kinds supports this. Each supports it differently.

Why the first version does not use it#

purpose.md states the price and control reasons. A third reason belongs to this file: the four kinds share nothing here, and interactive terminals are the one surface all four have in common.

What it would buy#

  • No screen reading of any kind, anywhere.
  • Structured state instead of inferred state. Three of the four protocols report turn state as typed events.
  • No startup screens. They belong to the terminal user interface.
  • No pane, tab or workspace management.

The shape it would take#

orcr gains a launch mode, not a second product. The socket API does not change. The same methods route to a different driver per kind.

The state vocabulary stays the same. Headless agents report state more precisely, not differently.

Two commands have no meaning in headless mode: orcr agent attach, because there is no terminal, and orcr agent interrupt, which becomes a protocol message rather than a key.

What must be decided first#

  • Whether a single agent can be started headless while others run interactive, and what orcr agent list shows when both exist.
  • Whether the transcript reader stays the same. Three kinds write the same transcript in both modes. Confirm the fourth.
  • How model and effort arguments map, since some protocols set them per request rather than at launch.

Note the shape difference. Three kinds run one process per agent. OpenCode runs one process for all agents. That difference alone changes process supervision, and it is the main reason a headless design needs its own pass rather than a flag.

Headless: Claude#

The interface#

Claude Code exposes a control protocol on standard input and output.

claude -p --input-format stream-json --output-format stream-json --verbose

The framing is newline delimited JSON. The controlling program writes control_request objects and reads control_response objects, interleaved with the message stream.

{"type":"control_request","request_id":"r1","request":{"subtype":"initialize"}}

The published Agent SDK starts this exact command. Using the protocol directly and using the SDK are the same thing at the wire level.

What initialize returns#

The initialize response carries the model catalogue, and two fields that matter for state:

  • pending_permission_requests
  • pending_user_dialog_requests

Those two fields report whether the agent waits for a person. A headless Claude reports that state as data.

Verified: an initialize request emits one control_response and exits, with no assistant frames and no result frames. It starts no turn and costs no tokens.

Sending a message#

Write a user message object to standard input. There is no composer, no Enter key, and no question about whether the text landed. The protocol answers that.

State#

Turn state comes from the message stream rather than from a screen. There is no fallback case and no rule engine.

Transcript#

Claude writes the same transcript file in both modes, at $CLAUDE_CONFIG_DIR/projects/<resolved cwd, every / replaced by ->/<session-uuid>.jsonl.

One warning carries over from interactive mode. Any supervisor must scrub CLAUDE_CODE_* from the environment it passes down, for the reason agents/claude.md gives.

Not verified#

  • Whether --bare skips session start hooks, which dominate the startup time of the initialize probe.
  • Whether the interactive transcript and the headless transcript are byte identical for the same conversation.

Headless: Codex#

The interface#

codex app-server

JSON-RPC over standard input and output. The handshake is initialize, then initialized, then ordinary method calls.

Some methods require the controlling program to declare capabilities.experimentalApi: true during initialize. Without it they are rejected.

Process shape#

Verified: codex app-server is a plain subprocess, not a daemon. Closing its standard input ends it, and it takes its whole process tree with it. There is no port and nothing to clean up.

A separate daemon does exist, behind explicit subcommands. A supervisor that does not call those subcommands never creates one.

State#

Codex reports turn state as typed events, including a variant for waiting on approval and a variant for waiting on user input. That is the structured form of blocked, which the interactive mode can only infer from the screen.

Model catalogue#

model/list returns the models and, for each, its supported effort values with a description string. agents/codex.md records why orcr reads the same data from codex debug models instead.

Transcript#

Codex writes a rollout file at ~/.codex/sessions/<year>/<month>/<day>/rollout-<timestamp>-<uuid>.jsonl.

Not verified#

  • Whether model/list pagination matters. It returns a cursor, and today one page holds every model.
  • Whether the rollout file layout is identical between headless and interactive runs.

Headless: Pi#

The interface#

pi --mode rpc

A newline delimited JSON duplex stream on standard input and output. One process serves one session.

Requests look like {"id":"1","type":"get_available_models"}. The type field names the operation.

Model and effort catalogue#

Two useful calls:

  • get_available_models returns the catalogue with cost, context window, provider, and a reasoning flag per model.
  • get_available_thinking_levels returns the effort values for the model the process was started with.

The second is per process, not per request. Verified: with 30 models that is 30 spawns, each about two seconds. agents/pi.md states why, and it states how thinkingLevelMap resolves.

State#

Pi has the strongest state reporting of the four kinds even in interactive mode, because its herdr integration pushes full lifecycle state and screen reading is skipped entirely. A headless Pi can report the same state through the RPC stream.

Transcript#

Pi writes a JSONL session file under ~/.pi/agent/sessions/<mangled-cwd>/. Its herdr integration reports the session as a path rather than an id, so the transcript location is known from the moment the agent starts. Pi is the only kind where that is true.

Not verified#

  • Whether the RPC session file and the interactive session file have the same layout.
  • Whether --no-session changes what is written to disk.

Headless: OpenCode#

The interface#

OpenCode differs from the other three kinds in shape, not only in protocol.

opencode serve --port <n>

This starts an HTTP server that serves every session. The other three kinds run one process per agent. A supervisor therefore manages one long lived server plus N logical sessions, rather than N processes.

Sessions are created and driven over HTTP. Events arrive on a server sent event stream. An event cursor exists, so a controlling program that reconnects can resume rather than lose events.

There is also an ACP interface:

opencode acp

ACP session creation returns the flattened model list, where each entry is the exact string the model argument accepts, including the effort variant. Verified: its startup took about twenty seconds, against about half a second for the fast paths of other kinds.

Model catalogue#

agents/opencode.md records where the catalogue comes from for this kind, and why it needs a server.

State#

The server reports session status and a separate asked-permission event. Those are the structured forms of working and blocked.

Transcript#

Storage is a SQLite database at $XDG_DATA_HOME/opencode/opencode.db, with write ahead logging. opencode export <session-id> renders one session.

Verified in interactive mode: a message submitted in the middle of a turn is recorded at submit time, not at turn end. The recorded time was 50.8 seconds before a running 60 second tool returned.

A note on builds#

A binary named opencode is not always OpenCode, so any work here must check opencode --version against upstream first.

Not verified#

  • Whether the HTTP event stream and the database agree on ordering under load.
  • Whether an invalid effort variant fails at launch or silently starts the base model.

A tmux backend#

What orcr uses now#

herdr is the terminal backend, and orcr requires it. herdr does four things:

  • It supplies sessions, workspaces, tabs and panes.
  • It starts agents.
  • It delivers keystrokes.
  • It reports agent state from per-kind detection rules that it maintains and updates.

Why someone would want tmux#

tmux is installed everywhere and people already run it. A tmux backend lets orcr work without asking a person to adopt a second tool.

What orcr would have to replace#

Only part of orcr is backend specific. The split decides how large this work is.

Backend independent, unchanged by a tmux backend:

  • Reading transcripts. Transcripts come from each agent's own files, not from the terminal.
  • The socket API, the command surface, and the state vocabulary.
  • Launch arguments, model and effort handling, and the model catalogue.

Backend specific, and all of it must be rebuilt:

  • Creating and addressing panes.
  • Delivering text and keys safely, including bracketed paste.
  • Knowing when an agent is ready, and when a message landed.
  • Knowing which agent occupies which pane after a restart.

The part that is not a port#

herdr maintains 22 versioned per-kind detection manifests with region scoping, rule priorities and negative conditions. They are updated as the agents change their interfaces. A tmux backend does not inherit them.

Replacing that is not a matter of writing regular expressions once. The agents change their terminal output regularly, and a rule that was correct last month silently reports the wrong state this month. Whoever builds the tmux backend takes on that maintenance permanently.

Two backends means two sources of state, and any place where they disagree needs an arbiter. Do not build a second backend without deciding, first, which one is authoritative.

A cheaper option#

If the goal is only to avoid asking people to install herdr, consider whether orcr can install and manage a private herdr instance itself. That keeps one backend and one set of detection rules.

What must be decided first#

  • Whether both backends can be active at once, or whether the choice is made once per installation.
  • Whether agent names stay unique across backends.
  • What replaces the per-kind detection manifests, and who maintains it.

External agents#

What orcr does now#

orcr controls the agents it started. An agent started by a person in their own terminal, or by another tool, is invisible to orcr.

What people would want#

Two things. One is easy and one is not.

Reading#

Show the conversations of agents that orcr did not start. List them, read their transcripts, and report their state.

This is close to free. Transcript reading is already backend independent, and orcr already converts four transcript formats into one shape. What is missing is discovery: finding transcripts on disk without a record of having created them, and deciding which working directory each belongs to.

One rule must survive that work. Never derive a working directory from a transcript path. Every kind mangles the directory into its path, and the mangling is lossy. Two different directories can produce the same path segment.

Driving#

Send messages to, interrupt, or stop an agent that orcr did not start.

This is not close to free, and it is where the risk is.

Why driving an external agent is different#

An agent that orcr started has known properties. orcr chose its flags, so it knows permissions are bypassed. orcr cleared its startup screens, so it knows the agent reached a usable state. orcr placed it in a pane it owns.

None of that holds for an external agent. It can wait on a permission prompt that orcr's launch flags remove. It can be in a mode orcr does not recognize. Typing into it can answer a question that a person was about to answer differently.

The failure is silent. A dialog consumes a message sent into it. The Enter key answers the dialog. Nothing reports an error.

What must be decided first#

  • Whether reading ships separately from driving. It should.
  • How an external agent is discovered, and how orcr decides which backend pane, if any, it occupies.
  • Whether orcr refuses to drive an external agent by default, and what makes it willing.
  • What orcr agent list shows, and how a caller tells the two populations apart. A field is needed, and it should be a property of the agent rather than a separate command.
